# v0.2.1.2 实验总结

调整后的计划已全部完成：新版 Astra 七题、新版 Luna 七题、同工程 v0.1 Luna 七题，共二十一个研究。Astra 的 v0.1 重测按用户要求暂缓。另保留了三项因工程问题中止的初测和一项获选产物有反例的旧轮次，没有按分数挑选重跑结果。

这轮的结论是：**当前工程与 v0.2.1.2 的组合，相对旧 goal 有综合收益；新增身份本身的稳定收益尚未证实。** 同工程 Luna 对照的正式耗时总体几乎持平，单题收益、退化和产物有效性差异都很明显。按此前约定，以 goal 为参照的扩展条件已满足，因此没有触发“方法最终无效”时的 v0.2.1.1 五题补测。

## 实现与执行

在 v0.2.1.1 上增加一名综合研究员，以及算法与计算结构、布局与访存、执行与编译三种 KernelBench 研究偏好。四人都独立完成完整任务，身份不是局部分工。通用身份属于 RSI，GPU 身份位于 example；版本化 Markdown 随冻结配置装配，恢复时仍保留。观测到的二十一次 researcher compact 中，十九次直接保留完整身份，两次在下一次模型输出前恢复，没有观察到身份丢失。

共同工程修复包括：明确 ID 的原子批量撤回、结束边界对已受理撤回的处理、leader 依据原始证据撤回错误候选、经验来源类型修复、真实文件执行诊断脚本，以及减少不必要的恢复状态重建和历史作业扫描。已完成针对性验证，实验后期普通工具维持在约一秒上下，没有重现持续 5–10 秒的阻塞。Luna 新旧两组使用同一 r4 工程；Astra 初测修复与重跑的差异在单独复盘中保留。

每题四名 researcher 各获得 3600 秒有效时间，正常推理、编译和 GPU 执行计时，API 故障与 GPU 排队扣时。全部二十一个研究的四人预算、获选验证时刻、源码对应和撤回状态检查通过。全局并发峰值为三题，包含最终确认；结束时所有研究及补充 GPU 作业均已终止。研究期间没有向模型补其他 run 的发现。

工作台分组为 `v0.2.1.2-astra-初测-r*`、`v0.2.1.2-astra-扩展`、`v0.2.1.2-luna` 和 `v0.1-luna-工程修复后`。Luna 两组各七题。

## 相对 goal 的结果

比较候选耗时，越小越好。探索与同一小时有效时间内的探索最好比较，最终复测单列；不用波动的 reference 把界面 speedup 当作跨 run 性能依据。

| 组别 | 正式最终通过 | 正式探索性能比几何平均 | 排除已知输入 / 参数反例后的探索对照 |
| --- | --- | --- | --- |
| v0.2.1.2 Astra | 7/7 | 1.166，七对，五胜两负 | 1.316，五对，五胜零负 |
| v0.2.1.2 Luna | 6/7 | 1.576，五对，五胜零负 | 1.739，四对，四胜零负 |
| 同工程 v0.1 Luna | 6/7 | 1.186，五对 | 0.873，仅两对，零胜两负 |

比值大于 1 表示该组比同模型 goal 更快。分母不同，后两列不能当作同一七题平均互相替代。Luna 的 L3P10 三种方式都没有正确结果，L2P14 两个新组有正确结果而 goal 没有，不为缺失结果虚构比值。v0.1 Luna 的 L1P63、L3P28 正式获选源码有参数更新反例；旧 goal 的一些产物也在相同检查中失败，所有正式分数仍原样列在各题报告中。

Astra 的优势并非只有 L3P10：去掉它，六题正式平均仍为 1.094，其中四个无已知反例的对照为 1.233。不过该题的一小时边界确实敏感：goal 的 10.9 ms 在第 59.66 分钟，9.28 ms 在第 60.50 分钟，不能混用两小时最终成绩。Luna 去掉收益最大的 L3P28 后，三个可比探索对仍为 1.271。上述都是本次实验观察，不是统计显著性的证明。

完整数值和轨迹：[Astra 七题](v0212-astra-review.md)、[Luna 新版七题](v0212-luna-review.md)、[Luna 纯 pass@4 七题](v01-luna-review.md)。

## 同工程 Luna 对照告诉了什么

六个正式耗时对中，新版四胜两负；探索平均 0.9988，最终 0.9895，整体几乎持平。剔除纯模式两份已知参数反例后，剩余四题的平均为 0.793 / 0.779，新版落后，主要是 L2P14 的差距。这个子集同样不能代表七题整体：无效产物也是纯模式的失败，不能在汇总时悄悄忽略。

具体过程比平均数更有解释力：

- L2P71 的共享将不同研究员的 K 分块、精度、输出布局和后处理组合起来，新版 0.391 ms，纯模式 0.524 ms。传递能落到具体代码的局部改进确实有效。
- L2P14 纯模式第 37 分钟解决正确性，然后优化到 4.87 ms；新版到第 57 分钟才通过，停在 20.4 ms。leader 接收诊断太迟、把某份 GEMM 的结论扩大到其他实现，拖慢了关键路径。身份没有自动解决这个问题。
- L1P77 纯模式融合零值写回与活跃输出，获得比新版更好的结果；新版则通过同伴反例和 leader 撤回排除了错误缓存。速度收益与正确性清理是不同维度。
- L3P19 新版后期落后的综合研究员独立融合训练 BN，最终反超；纯模式多次重复定位训练态问题。不能把这次独立反超全部算作 leader 的统筹成果。
- L3P28 新版早期就发现 CLS 依赖化简，但约二十六分钟没有有效进入 leader 认知；后来才发生有价值的共享与再融合。纯模式四人都知道注意力长度为 2，却始终沿完整路径优化。识别一个形状事实与真正推导输出依赖，是两步不同的研究。
- 纯模式也会提前宣布完成。自动继续使 L3P28 的领先者从 1.40 ms 继续到 1.13 ms。这个机制有效，但不能保证后续探索方向合理或产物完全正确。

没有同工程的新 Astra v0.1 组，也没有同工程 v0.2.1.1 去掉身份的单独控制组。因此本轮不能把四倍尝试、共同工程、已有协作和身份的收益分别估计，更不能仅凭突破者的身份名称归因。

## 正确性与评测覆盖

本次额外检查都在相应研究结束后，对精确冻结的 goal、新版、纯模式源码使用相同输入和操作，没有给研究员补信息，也没有事后换选来美化正式结果。

纯模式 L1P63 的版本缓存连普通 Parameter 替换也会失效；L3P28 加了对象 ID，普通替换通过，但 `.data.copy_` 更新后仍读旧权重，20 个输出全部超阈值。对应 goal 和新版通过同一检查。这些是实际产物的参数语义问题，不是 GPU 排队、计时或选优遗漏，也不据此推断作者的作弊意图。

L3P19 还揭示了另一层覆盖缺口：Luna goal 搜索、goal 最终、新版、纯模式四份源码都遗漏 BN 计数更新；纯模式还遗漏运行统计，训练后切换 eval 输出失败，其他三份通过该输出检查。正式评测仅覆盖训练态前向，所以保留原成绩并另列状态问题。报告中的“排除已知反例”不是完整模块语义认证；进一步去掉这个状态问题题目，会减少可比样本，不能伪装成全七题结果。

## 后续建议

优先让首次正确、重大性能变化和具体错误可靠进入 leader 视野，附原始候选与作业引用。现有系统已经保存这些事实，主要缺口是没有稳定地进入决策过程，而不是再给 leader 堆一长段职责说明。

共享时保留结论对应的具体实现和适用范围；某个版本的 GEMM 对齐，不代表所有研究员的 GEMM 都对齐。把已经复现的具体产物错误，与尚未解决的方向性风险分开处理，避免“负面经验只允许一个接收者”挡住必要的错误通知。

这些属于下一轮可单独测试的改动，本轮没有热改配方，也没有恢复已暂缓的 Astra v0.1。现在适合保留当前版本继续做有明确对照的增量实验，尚不适合宣布人设方案已经稳定优于纯 pass@4。
