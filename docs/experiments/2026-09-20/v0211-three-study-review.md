## 工程修复有明确效果，但延迟仍未完全消失

原生 journal 的输出 token 含推理。最外层工具等待来自 Codex rollout 的 call/output 时间区间并集，
不把后台 GPU 进程的整个生命周期算成模型阻塞；新旧采用同一算法。

| L2P71 纯 pass@4 | exp-2 | 本轮 | goal baseline |
|---|---:|---:|---:|
| 每人输出 token | 55,724–60,612 | 79,305–85,995 | 76,547 |
| 每人推理 token | 21,672–27,154 | 43,383–45,804 | 37,593 |
| 每人最外层工具等待 | 20.3–22.9 分钟 | 4.4–5.4 分钟 | 10.9 分钟 |
| 四人正式探索提交总数 | 221 | 278 | 单人条件 |

原生 rollout 的末尾 usage 比 Runtime journal 可能多最后一次被取消时的少量输出；这里 token
统一使用已归档 Runtime usage，等待使用 rollout。差异不影响结论。

本轮两项协作研究的每人输出也达到约 7.5–8.3 万，工具等待约 5.1–7.1 分钟。
十二名 researcher 均只有一个原生会话，没有 compact。有效时间约 3600–3612 秒，
API 故障扣时为零，GPU 排队每人约 11–22 秒，墙钟约 60.2–60.5 分钟。
整体启动至最终确认约 61 分钟。这轮无法再用“每人少了四分之一输出”解释算法差距。

仍有可测的后期延迟。比较同名的普通工具，而非混合 GPU 等待：

| 工具，researcher 合计中位耗时 | 前 15 分钟 | 最后 15 分钟 |
|---|---:|---:|
| 新协作 L2P71：submit_report | 0.42 s | 5.37 s |
| 新协作 L2P71：withdraw_candidate | 1.19 s，早期仅一次 | 10.50 s，61 次 |
| 新协作 L1P63：submit_report | 0.51 s | 7.08 s |
| 新纯 pass@4：submit_report | 0.47 s | 6.22 s |

exp-2 同名 submit_report 的末段中位数分别约 14.94、17.63、23.93 秒，已改善但没有消除。
这些是原生调用到返回的总耗时，不能未经进一步 profiling 全部归因于某个函数。
后台 CLI 让模型避开了许多同步等待，但协调/记录工具的迟缓仍影响末尾处理。

另有具体诊断入口问题：`client.py` 用 `exec(compile(..., '_rsi_diagnostic.py', ...))`
包装脚本，脚本内的 `@triton.jit` 因无法读取真实函数源码报错。两项协作研究各有三名研究员
遇到相关失败，之后将诊断 kernel 放到 `model_new.py` 再 import 绕过。问题存在于诊断包装层，
不是模型不会写 Triton，也不是本轮 API 波动。CLI 的名字对齐不代表行为已完全对齐。

## 纯 pass@4：连续探索恢复，已经有两条路线超过旧 goal

探索最好耗时：R1 0.252、R2 0.261、R3 0.387、R4 0.311 ms；goal 为 0.277 ms。
团队最终为 0.254 ms，对比 goal 最终 0.280 ms，耗时减少约 9.3%。单批结果仍不证明统计优势。

R1 的关键不是早期偶然命中：约第 36 分钟到 0.270 ms，第 57 分钟通过显式布局和合并 MMA
等待到 0.266 ms，第 58.6 分钟调整权重加载顺序到 0.252 ms。R2 则独立探索预打包、TMA 输出、
转置点积和寄存器限制，最终 0.261 ms。两个人都在后期继续突破。

R3 虽仍落后，但输出 79,305 token，并不缺思考时间。它早期就选择 BF16 三分量六项乘法，
投入更高精度的实现，最后 0.387 ms；R1/R2 的快速方案主要为两分量三项乘法。
R4 也独立投入数值压力、范围保护和 TF32/FP16 补偿路线，最后 0.311 ms。
这说明剩余差距更多在算法、精度选择和验证投入，而非统一的工具吞吐不足。
不能据正式随机测试通过推断任何快速方案覆盖所有数值边界；本次未给 baseline 和新 pass@4
候选追加统一对抗测试。

## L1P63：有清晰的协作收益，也保留了不同方向

四人探索最好为 5.57、4.78、4.69、6.08 ms。R1 保留常驻权重方向，R2/R3 发展打包卷积与
TMA/WGMMA，R4 将 Winograd 从首版 53.4 ms 改进到 6.08 ms。没有把落后者一律换成领先代码。

有实际采用记录的共享：

- R1 的 BF16 hi/lo 表示经 leader 传给其他人。R3 明确报告受此启发，将其用于自己的
  NHWC 隐式卷积，从 16.2 ms 改进到 7.19 ms，再到 6.08 ms。
- R1 的异步三次 WGMMA 后统一等待，被 R4 用于自身一维 Winograd；R4 再改三缓冲，
  从自己的 Gluon 首版 29.9 ms 改善到 8.12 ms。收益由共享机制与其独立实现共同产生。
- R4 的共享内存切片错误是本轮最好的一次协调案例：约第 46 分钟怀疑跨 warpgroup 竞态；
  leader 只把问题转给 R1。R4 加 barrier 后误差完全不变，主动修正归因，leader 同步更正。
  第 51 分钟 R4 验证了转置权重再切片的修复。R3 此时独立遇到类似错误，leader 才把已验证
  的修复给它；R3 在约第 56 分钟恢复正确性，随后继续自己的性能路线。

该案例符合本次预期：负面线索小范围核查，解决方案再扩大共享；接收者核对原始证据，
没有因 leader 的第一种解释就把全部候选都当作有错。

仍有浪费：R4 整体耗时一直偏高，leader 虽分享局部机制，但没有系统比较其关键瓶颈是否
仍有足够改进空间。也不能反过来以其最后落后证明应该提前停掉 Winograd。
当前收益来自信息复用，并不意味着 leader 已掌握可靠的研究资源分配策略。

## L2P71：共享限制生效，数值审查仍会成为共同工作

成功传播的 problem 按经验 id 都只增加一名接收者，未见 leader 通过换 id 扩散同一反例。
关键数值问题的时间线（相对整题启动）：

1. 第 49 分钟，R2 发现 seed 1234、全尺寸 x=65536 下两分量三项方案的反例。
   leader 先要求原作者处理，只把未解决问题转给刚引用该源码的 R3。
2. R2 独立实现并验证六项修复，正式通过，补充反例测试也通过。
3. 第 56 分钟，leader 沿用原经验 id 标记 positive，将修复及其适用反例分享给 R1。
   这是规则允许的传播，不是额度逻辑失效。
4. R1 到约第 59 分钟确认自身同类错误，开始修复和清理历史候选；R4 继续自己的
   TF32 高低位路线，最终 0.357 ms，没有被要求重复 BF16 修复。

比 exp-2 有改善：正式探索提交 168→223，诊断 70→35，撤回记录 118→68，指导调用 53→34。
但这不能全部归因于 Prompt，因为同轮同时更换 CLI 并修复吞吐。共享限制控制了问题扩散的
时机与人数，无法保证已验证修复不会使多人进入相近工作，也无法决定本题额外数值审查的边界。

尤其要区分“共享一个有帮助的修复”和“接收者必须重新做诊断、撤回几十项旧候选并迁移实现”。
后者仍有较大成本。本轮 R1 收到修复时只剩几分钟；leader 明确要求先撤回当前最好再处理其他
派生，但当前工程接口使这一清理无法可靠地完成。

## 最重要的残留问题：报告说已撤回，不等于系统全部撤回

R1 末尾报告称所有 BF16 两分量三项候选都不再作为有效最佳，但真正完成的该系列撤回只有
0.291、0.293、0.294 ms 三个候选。第四次撤回在预算停止附近被打断。
系统随后选择了仍未列入撤回集合的 `candidate_162ed02a04cf5e7a6f2f1fc8`，探索 0.295 ms，
最终 0.293 ms / 5.3925×。

冻结最终源码仍为相同的 BF16 两分量三项计算，没有六项修复。与已经发现反例的源码相比，
主要差别为向量化 BF16 转换和等价激活写法，未修复共同的精度缺项。它属于 R1 声明要排除
的系列；但没有在此次分析中给这个精确源码再运行反例，不能把静态判断伪装成新增实测失败。

已保存的其他路线中，R4 的 0.357 ms（探索 4.3697×）、R2 的 0.385 ms、R3 的 0.405 ms
分别是报告确认保留的最好。0.357 ms 尚不是重新做过最终复测的替代成绩，不改写历史 5.3925×。

系统遵守了已收到的撤回记录，问题在于候选撤回只能逐项表达、耗时随历史增长，且预算结束
可以截断尚未完成的清理。通用修复应是一次提交一组明确候选 ID 的原子撤回，保留原因和引用；
对仍待核实的候选也应有明确的暂不参与最终选优状态。不要让收尾依赖解析报告里的自然语言。
