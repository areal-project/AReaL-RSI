baseline 的关键过程是：普通 TF32 正确性失败后，继续尝试 tf32x3，通过正式校验；然后调整 tile 和地址计算；后期把 72 项归约改为 K=64 加 K=16 的尾部，从约 0.49 ms 降到 0.402 ms。其约 11、12、18、50 分钟的正式结果分别为 0.757、0.562、0.501、0.402 ms。

本次 R2、R3 的最好实现仍走 IEEE dot 路线；R4 的最好实现使用直接 FP32 累加。R3、R4 都试过普通 TF32，并观察到约 5.5e-4 的正确性误差，随后回到慢一些的路线。本次纯模式没有成功完成 baseline 中“普通 TF32 失败 → 测试 tf32x3 → 继续优化归约布局”的完整探索链条。

旧 pass@4 的赢家使用 tf32x3，但另外三人的 IEEE 实现也达到 0.584–0.628 ms。因此不能把全部差距简化成一个精度选项；地址、布局、归约组织及调参是否形成有效实验同样重要。

**R1 有一例可以从源码直接证明的无效实验。**

个人有效时间约 50.89 分钟，R1 对外表示：

> `tf32x3` 是 Triton 官方提供的三次 TF32 分解路径；在本题 5/5 正确性测试中通过，但速度与 IEEE 路径相同，因此没有带来收益。

对应正式候选为 `candidate_8b34d0a10699829d092b458d`，源码 SHA256 为 `a2a0714ba0af259412afcbe9631ac8c8fcda848a64ed297bad1334d070690772`。

冻结源码显示：

- 第 60 行：`_im2col_gemm_kernel` 中改为 `input_precision="tf32x3"`。
- 第 110 行：`_conv3x3_fused_kernel` 仍是 `input_precision="ieee"`。
- 第 135 行：`ModelNew.forward` 实际只调用 `_conv3x3_fused_kernel`。

它改了没有被执行的函数，随后将原 IEEE 内核的 2.97 ms 结果解释为 tf32x3 没有收益。这里不是评测器测错、缓存用错源码，也不是 leader 的误导，而是研究员没有核实修改是否进入实际执行路径。

这说明 R1 的 44 次正式评测不等于 44 次有效检验不同假设。此例足以证明一项具体研究错误，但不能单凭这一例证明所有退化均源自同一个原因。

**计时仍有一个明确的缺口：流式连接超时前的等待没有追溯扣除。**

新 pass@4 R3 的独立 HTTPS relay 记录到两个模型服务连接 TimeoutError，均有约 300 秒没有网络字节传输：

| 北京时间连接开始 | 超时断开 | 连接历时 |
| --- | --- | ---: |
| 22:03:50 | 22:08:56 | 306.21 秒 |
| 22:17:31 | 22:22:37 | 306.11 秒 |

Runtime 只在超时已发生后发出 `apiAvailable=false`，恢复后累计扣除 43.82 秒；这两个失败请求之前的约 10 分钟没有进入 API 故障扣除区间。按“失败请求及重试不计有效时间”的目标口径，这名研究员实际上只获得约 50 分钟，而非完整 60 分钟。

相同模式还出现在新 v0.2.1.2 的 R1、R3，以及新 skill 组的 R2，各一次、约 5 分钟。新纯模式 R1、R2 没有这种 relay 超时，仍明显不如历史结果，所以不能用这项缺口解释整组退化。

实现层面，Runtime 已有 HTTP 请求开始/失败/恢复的计时转发，但本次这些流式超时只落到了普通 availability 事件，没有落到带原始请求开始时间的 `apiRetry` 事件。需要补齐流式失败这一种故障路径；不能将所有正常模型推理等待都排除，也不能将所有 HTTPS 连接时间一律视作故障。

GPU 排队不是主要瓶颈：本次纯模式各人累计排队约 9–11 秒。R2–R4 的单次作业中位耗时约 9.1–9.2 秒，与旧组约 8.9–9.3 秒接近。R1 约 12.2 秒，部分来自它自身较慢的实现和实验开销。

**已核对相同的部分，以及目前无法证明的部分。**

- 两次纯 pass@4 去除 run 路径后的 RSI developer prompt 一致；原生 rollout 中的完整初始 developer 内容也一致。
- 原生基础指令 hash 相同，Codex CLI 均为 0.153.4。
- 请求配置均为 `gpt-5.6-luna`、`xhigh`、同一 API base URL、AReaL Agent Runtime 的 codex-cli 后端。
- RULES.md 和 reference.py 内容相同。初始任务描述只有组名标题多出 `pass@4`，正文一致。
- 两组 leader 各只有 4 条初始任务消息，没有后续技术指导或跨研究员经验转发。
- 本次网络转发比早晨多了超时退出与日志记录机制。这是已知工程差异，前面的流式故障计时仍未覆盖完整。

因此，纯模式的此次退化不能归因于新增人设、profile skill 或 leader 分享经验。也没有发现本地请求意外从 xhigh 改低、换了模型名，或题目规则被改写。

本地请求配置相同，不等于能验证上游实际权重、路由和负载相同。输出量下降与推理中的明显错误值得继续调查，但现有数据不足以证明“高强度测试触发 API 降智”。同样，也不足以证明这只是独立随机波动。

与 goal baseline 仍有流程差异：baseline 使用原生 goal 控制并以英文给任务，RSI 使用研究员 developer prompt、RSI 工具和系统续跑消息。baseline 有 20 次正式评测及 60 次诊断，当前纯模式以直接正式评测为主。baseline 的诊断还多次使用 seed 137，而当前规则将其保留给最终复测。这些差异需要保留记录，不能声称二者是完全相同分布的四次抽样；但它们不能解释同一天两次纯 pass@4 的全部变化，因为后两者的提示和规则没有上述差异。

**建议优先处理的事情。**

1. 补齐流式连接超时的追溯计时，并将本轮受影响研究员标为有效时间不足；不要悄悄改写历史分数。
2. 暂停继续堆叠 leader 或人设修改。先用当前 API 重跑一次字面复用既有 goal baseline harness、query 和工具的 Luna L2P71；同步或相邻时间运行固定输入的 RSI 单研究员对照，记录请求失败区间、输出量、实际候选源码和突破时间。
3. 若当前原生 goal 也稳定退化，优先排查共同的上游服务和模型执行环境；若 goal 能复现而 RSI 单研究员不能，再分离 query、续跑方式和工具上下文。待单研究员可对齐后再比较 1 与 4 的并发影响。

本轮结果更支持“研究决策和实验有效性下降，加上未完全解决的吞吐/计时问题”，而不是“leader 功能一定导致退化”。仍缺少上述同期原生 goal 对照，无法给出唯一根因。
