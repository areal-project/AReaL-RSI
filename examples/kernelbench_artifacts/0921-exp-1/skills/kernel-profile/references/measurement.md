# 计时与实验设计

## 先确认比较的是同一个工作负载

记录实际 shape、stride、dtype、device、模型 training 状态、输入和参数的构造方式。
模型可能更新统计量或缓存，重复 forward 不一定无副作用。比较两种实现时，先确认它们
从等价状态开始；不要为消除状态变化而擅自改任务语义。计算和输出依赖仍应完整保留。

第一次调用可能包含编译、自动调参、初始化和缓存准备。先预热并同步，再测稳定调用。
若任务关心首次调用成本，则另行记录，两种成本不要混成同一个数字。
诊断脚本的配置仅是起点，最终以本题规则和正式评测为准。

## 看懂时间表

算子的 total time 可能包含子操作；self time 扣除了子操作。同一段执行在父子行里
出现多次，不能直接相加。GPU kernel 表还要结合调用次数看：一个 100 微秒的 kernel
调用 100 次，与一个 10 毫秒的 kernel，对应的改进可能完全不同。

多流执行有重叠时，kernel 时间之和也不等于端到端时间。CPU 表中的高耗时可能是等待
GPU，同样不能直接解释为 CPU 是瓶颈。GPU 总耗时解释不了端到端耗时时，才进一步
查看同步、分配、host 调度和 launch 间隙。需要时间线时用脚本的 `--trace`；输出文件
留在远端工作区，主要 GPU 摘要会打印到日志，当前 CLI 不保证自动下载 trace。

## 不开 profiler 的计时

CUDA event 适合比较同一 stream 上的设备执行区间。预热之后记录 start/end event，
等待 end 完成，再读取 elapsed time。一次测量太短时，在区间内重复多次并除以次数。
独立重复几个区间，报告中位数和波动，而不是只取最小的一次。

若有其他 stream，确保 end event 之前已经等待被测工作完成；否则会漏计。
用 CPU 时钟测完整调用时，在边界同步，避免把异步 launch 的返回时间当成执行时间。
分段插入同步会改变重叠和流水线，只适合诊断，不能把这种分段结果冒充原实现的端到端耗时。

反复跑相同输入会形成热缓存，生产或评测未必如此。不要擅自改变缓存条件来制造优势。
诊断说明当前条件即可；正式成绩由既定评测流程确定。

## 让一次实验回答一个问题

以已保存的实现为 A，修改版为 B，在同一诊断作业中交替测 A/B/A/B，观察顺序影响。
先保证输入、输出和状态一致。无需把大量参数组合塞进一个长作业；优先选能支持或否定
当前解释的对照，之后再做必要的局部调参。

例如怀疑中间布局转换太贵，可以先测转换占比，再比较“显式转换 + 连续访问”和
“直接访问原布局”的完整路径。不能只测后面的计算 kernel，漏掉转换成本。

如果一个阶段占总时间的比例为 f，即使它无限快，整题加速上限也只有 1/(1-f)。
先考虑预期收益是否值得复杂度。这个估算在阶段重叠或新方案改变整个流水线时需要重算。

Profiler 会改变执行开销。shape、stack、内存追踪等信息按需要打开；测量解释与正式分数分开。
接口细节见 [PyTorch Profiler](https://docs.pytorch.org/docs/2.8/profiler.html)。
