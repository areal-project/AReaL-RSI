## 研究轨迹中的效率问题

1. **早期仍收束为同一路线的参数微调。** L2P71 的算法、布局、执行身份都收束到 K-major implicit GEMM，成绩约 0.708–0.717 ms。L1P77 在 packed 权重方案从 1.37 ms 改到 1.35 ms 后，leader 又于 17:54:54–55 分别把配置同步给另外三人。共享本身有效，但没有明显保留几条不同的优化假设。
2. **L3P10 的手动诊断改变了执行状态。** 算法、布局、综合研究员的 repro.py 显式对 reference 和候选调用 `.eval()`，而公开 reference 的构造函数并未切换到 eval。报告却将“手动对齐、正式失败”主要归因于参数同步。手动诊断并不能排除 train/eval 差异；约 18:00 后开始有人移除 `.eval()` 并补 training BN。尚未通过本次检查独立核实远端评测器所有行为，不能直接宣布评分器有 bug。
3. **leader 读轨迹成本高。** read_researcher_trace 返回最多 16,000 字符的事件 JSON，按字符切片，可能从 JSON 行中间开始；再经工具响应嵌套包装。L3P28 leader 于 17:53:17 错取 content 后得到四个 `chars=0`，随后反复解析/读取。各题 leader 第 16 分钟的输入上下文约 9.3–13.1 万 token，旧版同题约 3.1–11.0 万；读取增多不是资料包直接重复注入，首个输入仅从约 12.4k 增至 12.6k。
4. **编辑工具有可见的重试开销。** 截至约 18:03，检测到 465 次含 apply_patch 的外层调用中至少 34 次包含明确补丁/路径错误：同一 patch 删除再新增同一文件被拒绝、上下文不匹配、长绝对路径拼错等。不能把这些都归为平台 bug，但它们没有产生有效实验。

profiling skill 已实际使用：L1P63 执行研究员测到了自定义卷积单 kernel 约 83 ms；L2P71 执行研究员测到了参考卷积和后处理的时间拆分。它提供了真实证据，但目前还没有稳定改变全队的探索组织。

## 单独记录的评测有效性问题

L3P10 布局研究员在 `repro_seed.py` 中使用了预留最终种子 137，并于 17:58:10、18:01:00、18:02:33 调用 GPU 诊断。
这与当前 RULES.md 中“诊断不能使用专供最终复测的种子”冲突。
不能把此后的 seed 137 复测结果当作完全未见数据的独立复测。此项需要单独处理，不是效率下降的解释。

## 后续优先级

- 比较相同并发下的吞吐，避免把七题并发与三题并发的差异全部归因于人设。
- 为诊断提供与正式评测一致的初始化/执行状态说明或公共入口，减少研究员猜测评测条件。
- 轨迹工具直接返回可读的完整事件条目、明确时间和分页信息，避免 leader 自行解析嵌套 JSON/半截行。
- 协调重点放在不同的优化假设上。可同步关键修复和机制证据，不必让全队跟进每个微小配置变化。
- 不建议仅凭当前分数判定资料机制无效；也不应把本轮当作排除了并发因素的消融实验。
