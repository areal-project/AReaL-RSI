轨迹上的主要收益是团队接力：L2P71 算法研究员改 K64+16，其他人复现，最后执行研究员合并后处理再获得两次 0.391 ms；L1P63 布局研究员提出 NHWC 及新 tile，其他人继续独立验证。旧 goal 的 L1P63 源码 `bb02ec06…` 同样已有 NHWC 输出，但使用九次 IEEE dot 和每次 forward 的权重重排，新版使用三次 tf32x3 dot、直接读取原参数。因此跨轮性能差异不只来自输出布局，不能把全部增益归给某一个身份或分享动作。

这说明“知道 batch_first=False”与“沿最终输出追溯依赖、删除无关计算”是不同层次的发现。当前差距主要在研究选择，而非四人未获得完整环境；继续到三十五分钟，不能因为某路线暂时落后就结束独立对照。

### 最后一题三十五分钟：后起者领先，但参数缓存需要单独审查

约三十五分钟，四人正式最好为 2.51 / 1.43 / 1.50 / 3.05 ms，输出约 6.4 / 4.0 / 6.6 / 4.9 万 token。API 等待仍仅 R2/R3 的 25.5 / 34.4 秒；194 个本地作业、五次报告，没有协作动作错误。四份最好源码都仍计算完整 patch 和 Transformer 路径，没有新版的 CLS 依赖化简。

R2 和 R3 各自发现权重连续转置布局的收益。R2 原先落后，先以每次转置当前权重到 1.85 ms，再专门改善小 batch 分类头和 K=2048 线性层。随后两人都加入按对象 ID 和 `_version` 刷新的权重缓存，分别到 1.43 / 1.50 ms。这些后期源码已不同于第 23 分钟的无缓存版本；普通参数替换可以改变 ID，但 `.data.copy_` 不改变该判据，最终需要对精确获选源码与 goal、新版实施相同检查。不能把评论中的“版本变化就刷新”当成完整参数语义证明，也不提前认定已得到有效突破。

R4 的 cuBLAS 路径数值失败后恢复自定义 Triton。若干正式通过源码仍保留 cuBLAS 函数定义，但实际 forward 的调用全部是 `use_cublas=False`；仅凭关键词存在不能判定正式成绩来自库计算。R1 的融合尝试也多次失败并恢复原版本。保持冻结配置继续，不给研究员补其他运行的缓存反例或 CLS 结论；五十分钟再次审查。

### 最后一题五十分钟：继续机制有实际作用，缓存风险仍在

四人正式最好为 2.51 / 1.13 / 1.32 / 2.74 ms。输出约 8.2 / 5.4 / 8.3 / 6.9 万 token，310 个本地作业、22 次报告，API 等待没有继续增加，也没有协作动作错误。各自最好源码都仍是完整路径，尚未发现 CLS 依赖化简。

R2 曾在约第四十七分钟前给出 1.40 ms 的“最终完成”消息，系统自动继续后，将主 GEMM 的 BM64 改为 BM32，到有效第 47.81 分钟正式得到 1.13 ms。这证明监督继续确实避免了早停，但该候选仍包含对象 ID / 版本缓存，最终参数检查不能省略。R3 也保留缓存并调整不同线性层的 tile，到 1.32 ms；R1 的多次融合没有超过自己的 2.51 ms；R4 的 CUDA Graph 只通过四次随机校验，已恢复普通 Triton，再靠 BM32 到 2.74 ms。

继续至四人的完整有效预算及最终确认。之后对 goal 搜索、goal 最终、新版和纯模式最终源码使用同一参数替换 / 内容更新检查，所有正式成绩和失败尝试照常保留，不在运行中补同伴或其他 run 的信息。

### 最后一题完成及全计划收尾

约 11:50，L3P28 最终确认完成：探索 1.13 ms，最终 1.19 ms。四人的有效时间为 3600.28–3600.89 秒，215 个远端研究作业全部结束。获选源码在有效第 47.81 分钟验证，与最终回执一致，没有选优遗漏或预算越界。

同一参数检查确认纯模式 `18bce48c…` 的普通 Parameter 替换通过，但 `.data.copy_` 更新后仍读取旧缓存，最大误差 0.468878，20 个输出全部超阈值。goal 搜索、goal 最终和新版精确源码的三项检查均通过。保留正式分数并单列参数输出反例，不重新选择其他源码。四个补充作业也已结束。

同工程 Luna 七题完整比较：六个正式耗时对中新版四胜两负，探索 / 最终几何平均 0.9988 / 0.9895，整体几乎持平。纯模式 L1P63、L3P28 的已知参数反例剔除后，剩余四对为 0.793 / 0.779；不能将这个子集当作七题整体排名，正确产物的缺失同样需要报告。L3P19 的模块状态问题另外保留。

计划内二十一个研究全部结束，四人预算、获选源码与撤回状态检查均通过；工作台还保留三项工程中止及一项无效旧轮次，共二十五个执行记录。全局并发峰值为三题，最后运行数为零。冻结 r4 的二十六个源文件保持一致，研究期间未改配方。当前工程与新版相对 goal 达到约定的综合收益标准，但身份本身是否稳定优于同工程 pass@4 尚未证实。本轮没有触发 v0.2.1.1 条件补测，也没有恢复 Astra 的 v0.1。总报告与三份分组复盘已更新。

## 对照口径

Goal baseline 的 Astra、Luna 目录虽然带 `hour1`，L3P10 实际都运行到两小时。比较时从原始作业和等待记录截取一小时有效时间，探索结果与探索结果比较；两小时的最终结果另列，不混称为一小时对照。

另从原生累计 usage 记录截取相同的一小时有效边界，Astra goal 的 L3P10 / L2P71 / L1P63 输出分别为 73,387 / 76,547 / 70,926 token，包含 reasoning。新模式初测 r2 每人的输出约为 L3P10 79,033–81,611、L2P71 85,168–90,309、L1P63 79,941–89,429；L2P71 修复后 r3 为 84,242–91,144。本轮没有重现单 researcher 输出量显著少于 goal 的旧现象。两边取已报告的 token，末次 usage 可能略早于预算截止，不将其视作精确吞吐控制实验。此项证据也说明不能把相对旧对照的所有收益都归给身份机制。原始截取记录保存在 `baseline-tokens-1h.json`。

Astra L3P10 在第一小时内的最佳正确候选为 10.9 ms，约 59.66 分钟完成；9.28 ms 在约 60.50 分钟，7.0 ms 在约 64.02 分钟。一小时边界对这题影响很大，最终判断同时说明这一敏感性。

已核对前六题的最终获选候选验证时间，均早于所属研究员的预算停止时间，提前约 41–844 秒。没有把预算结束后才形成的候选计入这些一小时最好结果；记录见 `best-candidate-budget-audit.json`。

历史 goal 的选优并不总是选择候选耗时最短的源码。L3P19 当时以每次实测 reference 计算 speedup：最终获选版本耗时 0.616 ms，但其 reference 均值异常升到 4.83 ms、标准差 7.34 ms，得到 7.84×；一小时内更快的 0.501 ms 版本 reference 为 1.53 ms，只得到 3.05×，因此未被选中。L3P28 类似，获选 0.100 ms 的 reference 为 2.61 ms，首小时最短 0.0882 ms 的 reference 为 1.86 ms。本文主要使用旧轨迹中首小时最短候选耗时，避免将这些历史选优损失算作新协作的收益；两份源码不同，也不把最终测量差异全部解释成同源码波动。结构化原始记录见 `baseline-selection-audit.json`。
