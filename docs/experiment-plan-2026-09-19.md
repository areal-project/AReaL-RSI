# 9 月 19 日晚协作实验计划

状态：五个必做批次及逐批分析已完成，共 15 个研究；结果见[实验报告](experiment-report-2026-09-19.md)。没有版本晋级，条件 Astra 复测与 v0.2.8 未触发，具体理由已记录。
常规批次为三题：Astra L3P10、Astra L2P71、Sol L2P71。执行记录保存在 `.rsi/passk-workbench/operator/night-0919/`。下文保留启动前的实验设计与判断标准。

目标是验证：在相同模型和 researcher 预算下，leader 能否帮助解决困难，同时保留能带来后期突破的不同路线。
分数更接近、消息更多、正确性通过人数更多，都不是单独的成功标准。

## 调研结论

参考了 [Dream-RSI 实验想法](dream-rsi-experiment-ideas.md)。该文档保留原样。
以下区分论文的机制、报告的限制和我们准备检验的假设，不把相关工作当作本系统的效果保证。

| 工作 | 论文中的做法或发现 | 本轮可借鉴的部分 |
| --- | --- | --- |
| [Dream-RSI，§5.1、附录 B.2](https://arxiv.org/pdf/2609.14858v1) | 控制器结合分支轨迹、失败是否可修复和探索深度作出选择；ConvDiv 实验中，额外历史方向指导使两个被比较系统都退化 | 看连续证据，保留尚未充分验证的路线；共享局部事实时不要顺带宣布整条路线胜出 |
| [SwarmResearch，§2、§3.5](https://arxiv.org/html/2607.02807v1) | 全局 Shepherd 管理独立搜索者，通过起始候选、上下文和搜索类型影响探索；论文也报告了 leader 贪心收敛、指定具体思路，充分提示后仍存在局限 | 把“选择值得继续的研究问题”和“替研究员设计方案”分开；必要时从旧候选配合新上下文重新探索 |
| [PACEvolve，§3.1–3.3 及消融实验](https://arxiv.org/pdf/2601.10657) | 用近期改善趋势触发回退，清理上下文，并在自身回退与跨分支协作之间选择；消融中回退帮助弱分支，也可能损害最强分支的表现 | 停滞才审视是否重启，保留最强分支；reset 与共享限额分开试验，不直接按名次替换弱者 |
| [AlphaEvolve，§2.5](https://arxiv.org/html/2506.13131v1) | 候选数据库结合 MAP-Elites 与 island 思路兼顾成绩和多样性 | 保存不同路线的候选，不只保留全局最高分；今晚不实现完整进化搜索器 |
| [AI co-scientist，§3.2–3.3](https://arxiv.org/html/2502.18864v1) | Supervisor 根据系统统计分配工作，Proximity 对想法聚类去重 | 让 leader 看清路线、困难和剩余预算；判断趋同要看方法和实验，不靠分数接近推断 |
| [Magentic-One，§4.1](https://arxiv.org/html/2411.04468v1) | 区分事实、猜测和计划，持续检查进展与重复；停滞后重新规划并重置上下文 | 将一次建议之后的实际变化纳入下次决定；不照搬其串行发言和整队重置 |

Dream-RSI 的回放局限于已记录的搜索空间。我们的新建议会改变研究员后续行为，旧轨迹不能给出这种干预的反事实分数。
因此，历史轨迹只用于查找通用流程问题、检查当时信息是否足以支持决定；不能把离线回放结果当成新策略的真实成绩。
运行中的 agents 只能读取当前 run 获准的资料；操作侧的跨 run 分析、本文和历史解法不注入它们的上下文。

当前 v0.2.4 已有持续观察、进展视图、原始轨迹引用和可靠消息交付，但尚无共享人数限制或 leader 触发的会话重启。
`get_state` 的短视图主要展示最新报告、近期进展和近期作业；判断一条路线的潜力仍需要查看更早的连续证据。

## 固定实验条件

每个筛选批次是三个独立研究，并行启动：

| 研究 | RSI / researcher 模型 | 推理强度 |
| --- | --- | --- |
| L3P10 | gpt-6-astra | xhigh |
| L2P71 | gpt-6-astra | xhigh |
| L2P71 | gpt-5.6-sol | xhigh |

- 每题 4 名 researcher，每人 3600 秒有效时间；正常推理、调研、编译和 GPU 执行计时，已识别 API 故障与 GPU 排队按现有 `baseline-active-v1` 扣除。
- 不限制提交次数，不设置达到某个分数就提前停止。leader 随最后一名 researcher 结束。
- 一个筛选批次最多有 12 名 researcher 和 3 个 leader；不同批次不交叠。
- 同时进行的题目始终不超过 3 道，最终确认中的研究也占一个位置。每次启动前核对工作台全部运行状态；前批最终确认和分析完成后才开始下一批。
- 固定 Codex → AReaL Agent Runtime、原有 API/key、et15 GPUQ、硬件、任务、工具和网页搜索设置。
- 维持现有 fixed-reference-v1 探索计分，以及最佳有效候选一次 seed 137 最终复测。最终复测反馈不返回研究员。
- 角色 prompt 用版本化 Markdown；任务说明只随实验规则作必要变化，不写入从其他 run 得到的题目解法或提示。
- 每批单独分组，例如 `v0.2.5-screen-r1`；复测用 `v0.2.5-confirm-r1`。
- 启动前冻结源码快照、协作模块和 prompt 指纹、模型、预算、评测协议、校准记录与初始材料。不热改正在运行的研究。

## 对照与实验顺序

已有 v0.1 记录中，大部分题目使用 Luna 和一小时墙钟预算。当前工作台没有覆盖本轮三个模型/题目组合的完整同条件纯 pass@4 对照。
历史成绩保留作背景；不同模型、墙钟与有效时间、不同评测/工程版本不能直接作为严格协作消融。
外部 Codex goal baseline 属于 pass@1，不能代替这里的纯 pass@4。

第一批先按用户要求跑 v0.2.4。随后补一批当前工程实现下的纯 pass@4，仍用上述三题组合，标为 `v0.1-control-r1`。
后者保留 pass@k 的协作定义；新的计时、评测和通用工程修复明确记录，不能称为原始 v0.1 的完全复现。

初始工作 base 是完成工程检查的 v0.2.4，它只是共同起点，不预先认定优于 pass@k。
后续只有通过独立复测的版本才能替换 base。没有通过的版本留作独立实验，不默认叠加到下一版。

| 顺序 / 版本 | 相对 base 的主要变化 | 要验证的问题 |
| --- | --- | --- |
| 1. v0.2.4 | 当前实现原样运行 | 消息、进展可见性和持续观察是否实际可靠；没有这些故障后，剩下哪些协调问题 |
| 2. v0.1-control-r1 | 同一工程实现，关闭协作增量 | 相同资源下，独立 pass@4 到底有多强 |
| 3. v0.2.5 | 对同一经验实行单一新增接收者限制 | 降低传播范围能否保留不同路线，而不丢失有用的帮助 |
| 4. v0.2.6 | 根据连续证据选择介入对象和建议粒度 | 建议是否能切中接收者的困难，减少无依据换路线和过细指导 |
| 5. v0.2.7 | 停滞时受控回滚并重启少数 researcher | 新上下文和不同起始候选能否恢复有价值的探索 |
| 6. v0.2.8，条件项 | 更大范围的重启，或诊断所需的单独消融 | 默认只在 v0.2.7 不足以解除整队趋同且仍有预算时测试；具体内容在启动前冻结 |

若 v0.2.5 无效，v0.2.6 从 v0.2.4 出发；若 v0.2.5 通过复测，则 v0.2.6 可以从 v0.2.5 出发，并明确是在测试额外收益。
后续各版按同一规则选择父版本。v0.2.6、v0.2.7 的先后可以根据前批轨迹调整，调整理由先记录再启动。
不为凑齐版本数量强行执行没有证据支持的实验。

新增机制继续使用现有协作模块注册和版本选择，不另起 agent 后端，不改研究员独立完成整题的基本流程。
共享限额、决策记录和重启各自可开关；通用核心只使用任务提供的验证结果与预算，KernelBench 的计分细节仍留在任务适配器中。

## v0.2.5：限制经验传播

按用户给出的四人例子执行：**一条经验在整个 run 内，最多新增一名接收者**。源研究员 A 与接收者 B 合计两人。
限制不是“每条消息只发给一个人”，因为目前工具本来就是单人发送，连续发送三条仍会影响全队。

经验以简短结论、适用条件和原始证据引用登记身份；后续补充、改写与转述沿用同一来源。
leader 根据谁正在遇到相关困难选择接收者，也可以选择暂不共享。
A 的经验已给 B，不能通过 B 的转述再当成新经验给 C；同一经验给原接收者的澄清和纠正仍然允许。
leader 从 researcher 轨迹中自行总结的内容也计入该来源，不能换成“leader 自己的建议”规避限制。

实现上只增加当前 run 内的经验来源与接收记录，以及建议工具中的人数检查；不引入投票、多级审核或另一个常驻 agent。
系统能严格检查登记来源的接收人数，但简单的 ID 检查不能证明两段自然语言是否表达同一结论。
发现重复登记或未标来源时应记为规则失效，不能把此轮当作成功执行了限额的证据。

还必须区分传播与趋同：独立研究员可能自行得到相同思路，或者按现有权限主动阅读同伴记录。
本版保留当前按需读取同 run 资料的规则，记录实际读取与导入；不声称单独限制 leader 转发就能硬性保证多样性。
若主动读取成为主要传播途径，另开版本测试读取范围，不能在本版混入未声明的权限变化。

## v0.2.6：让建议围绕一个需要验证的问题

沿用已有状态、轨迹和 `update_plan`，补足 leader 作出介入决定时需要的一小份记录：
当前路线、近期已验证进展、实际困难、还没有得到回答的问题，以及上次建议的结果。
数据能由系统提供的就直接提供，判断由 leader 完成，不再增设评审 agent。

每次准备介入时，leader 要能说清：现在为什么需要帮助，这条证据为什么适用于这个人，下一次实验能回答什么问题。
如果对方正在执行一个明确且有希望的验证，保留它的机会。低分或暂时没有通过正确性不能单独成为换方向理由。
判断潜力也不能只凭 researcher 自称“很有潜力”，要结合实际代码、失败位置、局部结果或尚未检验的假设。

建议分两种粒度：

- 已核实的局部问题：可以给具体修复及原始证据，说明适用边界。
- 还不确定的研究方向：指出需要分辨的问题和一个可检验的尝试，不提前替 researcher 决定整套实现。

例如，分享“这个误差在某个中间结果已经出现，可以先检查你是否遇到相同现象”比“大家换成 A 的实现”更便于验证，也更少改写接收者整条路线。
leader 跟进实际结果；已读不算采纳，采纳不算有效。不要为了保持活跃而连续发送建议。
leader 继续主动观察、查资料和思考，不恢复阻塞 `wait`。

本版不硬性规定四人分别使用四种算法，也不按某个固定时间表强制换方向。
仅增加简短的决策依据和对应状态信息；不会把上述分析全文塞进 prompt。

## v0.2.7：回滚与新会话

停滞首先触发检查，不直接触发清空。尤其不能把 API 故障、GPU 排队、一次实现错误或者正常的大改写当作研究停滞。
建议将“近期约 15 分钟有效时间没有进展，且已完成至少 3 次有结果的实验”作为首轮检查条件。
这些是拟定的实验参数，启动前固定；是否重启还需要原始轨迹支持。
没有性能提升但获得了新的正确性证据、明确排除一个假设，仍可能是在前进。

两类情况分别处理：

- 3–4 人的核心方法与下一步试验都高度相似，且改善已停滞：保留最好的一条，优先重启其中 2 条重复路线；若另有一条不同且有潜力的路线，也保留它。
- 某人明显落后：先判断是可修复的实现困难、尚未完成的新方向，还是重复无效尝试。能用局部帮助解决的先帮助；不能根据排行榜自动 reset。

第一轮每个研究最多重启两个 researcher，每个槽位最多重启一次，逐个执行，不同时清空大多数人的研究状态。
重启时建议至少还剩 20 分钟个人有效预算，否则难以区分策略无效与没有时间验证。
如需要验证用户提出的更大规模回滚，再以 v0.2.8 单独测试保留一人、重启三人的策略。

重启内容：

1. 归档原会话和工作区，保留全部候选、实验与最佳结果。
2. 选择当前 run 内、尚有未充分尝试思路的历史候选；优先考虑该 researcher 自己的历史或公开起点。选择同伴候选时遵守所启用的共享限制。
3. 新建会话，从选定候选开始。保留任务、评测约束、剩余时间、必要的已验证事实和原始引用，不自动装回旧对话、旧 compact 摘要或积压建议。
4. leader 说明为什么选这个起点、哪些问题尚未验证，帮助进入状态；不发一套规定好的实现步骤。

仍使用原 researcher 的预算账户，重启、整理和重新理解任务的成本正常计入；不能通过 reset 再得到一小时。
同时运行的 researcher 不超过 4。运行中的作业与冻结输入、旧消息、新会话之间的关系必须清楚，不让旧作业覆盖新工作区。
原始会话继续可引用，不从历史中删除失败记录；最终选优仍能选到 reset 前的最佳有效候选。

当前已有候选快照和恢复代码的工具，但没有完整的 leader 会话重启操作。
这比限额需要更多工程工作，应单独验收预算继承、候选保留、旧上下文不回灌和作业归属后再跑模型实验。
如果结果无法区分是清上下文有效还是回滚有效，再单开“相同候选只重开上下文”的消融，不提前把每种组合都跑一遍。

## 每批分析与复测

每批三个研究及最终确认全部结束，先分析，再决定后续版本。分析至少交付：

- 逐模型/题目的最终有效加速比、探索最好成绩和首次正式正确时间；没有正确候选单独列出，不以零值比率混算。
- 每个 researcher 的有效时间、正常推理与实验、API 故障、GPU 排队；leader 的 token、调用和研究员消息处理开销。
- 以真实事件顺序构建团队最好成绩曲线，并映射到累计 researcher 有效时间。不能拼接各人的不同时间前缀制造不曾存在的团队状态。
- 四条路线的主要方法、尚未验证的问题、何时开始趋同。不同参数不自动算不同路线，相似分数不自动算同一路线。
- 对每次关键建议串起“来源 → 发送 → 已读 → 接收者动作 → 验证结果”，核实是否真的采用，以及解决问题还是放弃了有潜力的方向。
- 对 reset 记录起点、理由、剩余预算、新方向及后续变化；没触发 reset 的研究不能证明 reset 有效或无效。
- 区分实现故障、任务评测问题、协作机制未执行、机制执行后无收益，以及模型随机性。

建议后的提升只能表明时间上的关联；没有独立重复不能直接宣称全部提升由该建议造成。
不能仅依据正确候选人数上升或四人分数接近就认定解决了 pass@1 退化；还要看后续是否出现独立突破和团队最好成绩提高。

出现消息丢失、计时错误、错误冻结输入、选优错误等关键工程问题时，先修复和验证，再重跑受影响条件。
如果修复改变了所有模式的执行条件，对照也需要在相同修复下补测。原失败记录保留，工程失败不计为策略负面结论。
同一协作版本的工程复跑用 r2 标识并记录源码差异；改变协作策略或 prompt 则使用新版本。

初筛拟用以下规则分配后续算力：至少 2/3 条件相对当前 base 改善约 10%，没有正确性退化或另一条件超过约 10% 的退化，优先进入复测。
如果只在一个条件出现重大突破，也可进入专项复测，但不因此晋级为通用 base。
这些是实验调度阈值，不是统计显著性声明；差异接近测量噪声时按不确定处理。

有希望的版本立即插入独立 Astra/xhigh 三题复测：**L3P10、L1P63、L2P14**，仍为每题四人、每人一小时有效时间。
L3P10 是重新探索，后两题用于观察效果能否扩展；不能只重测之前保存的最好源码。
对应 base 或纯 pass@4 缺少同模型、同预算、同工程对照时，应补齐相应 Astra 三题对照，不用 Luna 成绩替代。

晋级看逐题表现和整体趋势：至少两题获得超过噪声的改善，第三题没有明显退化；总体相对 base 有收益，对纯 pass@4 也有竞争力。
小样本只支持暂时选择更好的工作 base，不能声称已经证明普遍优越。结果冲突就保留旧 base，追加针对性重复或停止这条改动。
新 base 的适用模型和范围写明；仅有模型特定收益时不扩张为全模型结论。

## 今晚的执行方式

优先顺序是 **v0.2.4 → 同条件 pass@4 → v0.2.5 → 分析决定 v0.2.6 或 v0.2.7**。
任何有明显希望的版本，其 Astra 复测优先于继续堆新机制。v0.2.8 属于条件项。

常规批次与三题复测均含 12 researcher 小时有效预算。
一小时有效时间不是一小时墙钟；批次还需准备、排队、API 恢复、最终复测和人工/代理轨迹分析。
因此按事件串行，不预先承诺某个整点启动下一版。用户已要求持续执行直到整个方案完成，不能以完成首轮或到达某个钟点为结束条件。
v0.2.4、同配置 pass@4、v0.2.5、v0.2.6、v0.2.7 均需完成实验和分析；条件版本、复测与必要工程重跑依据轨迹决定并记录。

正式执行时维护持久化批次清单，记录父版本、状态、run ID、冻结配置、结果与下一步理由。
后台程序负责计时、等待研究和最终确认结束、收集日志；我负责分析轨迹、修复问题和决定下一批。
下一批只有在前批分析落盘后才能启动，不能用一个固定 cron 脚本跳过分析直接连续提交。
恢复监督时从清单接续，避免重复启动或清空预算。新的筛选批次和 Astra 复测批次不并行占用 API。
出现工程故障先处理；出现策略问题可以修改后续计划或新增版本，但必须保存原结论与变更原因。

GPU 队列或集群入口异常时，已获授权通过 `ssh et15` 排查和修复；保留当前 run 的隔离、评测协议、预算和原始记录。
最后输出完整实验报告，逐版列出结果、轨迹证据、工程修复、复测结论、推荐 base 及不确定性。
