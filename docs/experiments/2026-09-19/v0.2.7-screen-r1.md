## 重启为什么一次都没有发生

本版在 v0.2.4 上仅增加 researcher_restart，没有叠加限额或决策记录。规则是在约 15 分钟无推进且已完成至少三个实验时审视；最新正确性证据、排除假设或正在完成的大改写都可以是进展。真正切换要求还剩至少三分之一预算、保留最好分支，每题最多两人、每人一次。

leader 一直把新诊断或新配置视为继续的理由。L3 在约半程写道“暂不重启，因为最近有新的后段 BN 证据”，约第 37 分钟又获得在线统计反证；之后越过了可重启窗口。Astra L2 各人持续有反例排除、资源诊断和新正确实现。Sol 从 Triton 转 CUDA，并有 Winograd 等失败但不同的尝试。没有出现工具拒绝申请或重启卡住：**原生调用次数就是零**。

这部分保守判断有合理性：不能因为 L3 没有正确分数就清空研究员，纯 pass@4 的赢家也是第 45.78 分钟才通过。但“任何新实验都算进展”又很容易让停滞永远不成立。当前策略没有区分“在变换参数”和“在关闭一个重要的不确定问题”，因而不能指望加一个重启工具就自动恢复探索。

不执行仅把重启上限从二人提高到三人的 v0.2.8：本轮并未碰到人数上限，增加上限无法检验这次观察到的障碍。也不临时强制清空以凑够重启样本。若下一轮专门研究 reset，应预先定义一次明确的审视窗口和实际选择依据，先确认有足够的干预样本，再谈更大范围的重启。

## Astra L2：反证共享有用，最后仍以独立布局改进取得最好结果

四人起初在收到技术建议前就选择 implicit GEMM / tf32x3，这不是共享引起的起点趋同。后续探索包括 BF16/FP16 分解、Winograd、显式布局和不同尾块处理。

R2 自己发现无缩放 FP16 分解对大输入产生 NaN 并撤回；leader 随后明确区分 FP16 值域问题与 BF16 省略低位乘积的误差。R1、R4 的三项 BF16 在正式随机输入上很快，但有符号、放大输入反例，leader 给出了具体复现条件，其他人分别检查并撤回。R1 后来的全局缩放 FP16 又遇到“单个巨大离群值压掉其他区域”的问题，leader 建议检查未受离群值影响的输出区域，R1 撤回并改成基于当前数据误差界的自定义实现选择。

这些事实来自本 run 自己的诊断，没有得到操作侧其他批次反例。也不能把所有舍入差异都当作省略运算：研究员用 FP64 对照区分了重排误差和缺项误差，leader 提醒不要无限扩张临时审核替代正式协议。

最好结果来自 R2 的 TF32x3 主块与尾块分开处理、方向及寄存器配置，最终 0.353 ms。R3 则沿六项 BF16、权重预处理、物理 NHWC 输出及尾块得到 0.369 ms。两个路线没有完全消失。另有一些非默认通道/形状检查超出了固定形状任务的主要目标，消耗了预算；这应通过任务明确适用范围，不能在 RSI 核心写入特定题目的捷径。

两份 L2 最终实现都通过操作侧同样的相消和值域补充检查。与 v0.2.4、v0.2.6 Sol 的值域反例不同，本版的较低正式分数不能单纯解释为“方法全面更差”，但也没有达到晋级标准。

## Sol L2：既有成功指导，也有过时信息和不成立的组合

早期 R3 的输出通道 × 空间方向快于其他人的转置方向，leader 传播后帮助部分人追上。但方向本身并不充分：R4 只转置仍慢，分离 batch 网格及静态展开后才改善。四人后续重复了不少相近 tile 组合，早期“接近带宽下限”的判断没有实测下界支持。

R3 转到手写 CUDA。首版 0.622 ms 虽通过随机检查，却自查出无效输出 lane 的 shared 越界读并撤回。leader 建议把安全修复与扩大 CTA 分开验证；扩大到 512 线程变慢，原 256 线程加安全修复为 0.619 ms。随后 epilogue FMA 为 0.608 ms，串行处理两组输出通道为 0.583 ms，leader 提出的 float4 staging 为 0.541 ms。这是可观察到的“建议—采用—通过—改善”链，不能说 leader 全程无用；单轮仍不证明全部收益由建议造成。

同时存在三个明确问题：

1. **同伴概览过时。** R2 在 20:01:41Z 的 get_state 只读到 R3 于 19:51:32Z 的正式报告：“0.622 撤回，正在修复”。0.619 和 0.608 的验证记录已经存在，公开进展也已更新，但同伴短视图没有最新验证/自动进展。R2 随后仍以“修复尚未验证”作判断，后来又从撤回版重新修复。原始读取权限正常，同期 R4 读候选已经知道新结果。具体证据见 stale-peer-state-audit.json。
2. **组合收益不可直接相加。** R1 独立去掉 shared 权重存储做到约 0.598 ms；leader 建议与 R3 的 float4/双通道组版本组合。R3 实际组合后为 1.43 ms，远慢于 0.541 ms，随后恢复。适用边界不同的局部优化不一定能组合，但这次有实测否定，并未撤回更好的旧产物。
3. **进展文字可能落后于工具结果。** R2 的作业在 20:21:38Z 已完整返回 succeeded、正确性通过、0.619 ms 和候选 ID，20:22:37Z 却说还在首次编译；20:23:43Z 才正确报告。实际编译约 72 秒，是正常有效工作，不是反馈丢失。调度需要优先使用作业状态和验证记录，文字用于解释。

也更正一项运行中的初步怀疑：leader 先把 padding 建议称为“尚未试过”，与已知负结果接近；随后明确区分完整 128×128 backing 与只 pad 宽度，研究员按新 stride 做了实验。后者不是完全相同的重复实验，虽然仍然变慢。

最后各人的最好分数仍有差距，领先者承担了大部分后续结构改进。按需共享已经发生，但并没有持续让所有人处于同一个可继续突破的基础上。

## Astra L3：局部反证及时传播，整题仍卡在早段统计

四人同样在建议前独立选择 NHWC / 自定义卷积 / BN 路线。约第 15 分钟已经有多个代表卷积精确匹配，后段 two-pass BN 在多个形状上也匹配；早段统计仍是主要障碍，完整正式检查一直未通过。

leader 的技术判断有两次需要纠正：

- 19:44:52/57Z 根据模板名把 128 当成线程数，向 R3/R2 给出具体归约假设；19:48:01Z 才建议查看实际 profiler launch；19:51:21/25Z 根据真实 512 线程证据向原接收人明确纠正。约 6.5 分钟内错误前提参与了搜索，但不能把期间所有工作都计为它造成的浪费。
- 20:17:01Z 宣称一个 CPU reciprocal 预测精确命中，20:17:51Z 读到实际输出后撤回这一数值结论。随后重新验证了二维映射下的构造输入，明确它并不代表随机激活已经匹配。

也有较好的协调：leader 在约第 29 分钟提出单个稀疏相消输入，R3 发现普通 sum 无法解释 reference 的均值。约第 37 分钟反例传给三人，分别尝试在线均值、分 batch 合并和二维映射。这个广播有原始证据、保留不同未决假设，不能简单归为扼杀多样性。

问题是闭环没有完成。后段精确统计约第 22 分钟已经共享，早段在线统计家族直到中后段才收紧；接下来二维样本映射、局部更新、跨线程合并仍有多个维度未验证。leader 到第 56 分钟还在提出新的权重乘法位置实验，最后完整误差仍约 1.6e-4–2.2e-4，没有正式正确候选。与控制第 45.78 分钟通过并留下约 14 分钟性能改进相比，分享大量局部发现没有更早关闭完整模型的正确性问题。

这支持“关键实验的选择和完整覆盖比沟通数量更重要”，但不支持认定四名研究员完全同质：它们确实检验了不同统计假设。没有 reset、没有 API 故障，不能把本轮失败归因于新会话工程或网络波动。
