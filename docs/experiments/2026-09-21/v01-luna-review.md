### 独立探索的优势与成本

L2P71 的四人确实走了不同路线，最后个人最好为 0.524 / 0.588 / 0.584 / 0.628 ms。R1 找到 tf32x3、独立 batch grid 和三个 K32 dot；R3 找到 K64+16 分块与连续权重复制，但保留 IEEE dot；其他人继续改善地址、tile 和权重布局。不同的有用经验各自存在，没有合成同一实现。新版通过共享把 K64+16、tf32x3、NHWC 输出及后处理改进接到一起，得到 0.391 ms。源码与实际接入记录支持这种解释，但一次对照仍不能证明全部差异都来自共享，更不能把协作加身份的整体收益单独归给身份。

L1P63 也并非四份完全重复的研究。R1 尝试自定义 CUDA shared-memory/FMA，R2 尝试完整 K 组织和不同输出布局，R3 优化固定形状的索引、tap dot 和权重布局，R4 使用 NHWC staging。R4 实际试过 tf32x3，正式正确但为 20.9 ms，慢于自己的 IEEE 路线，于是退回。它不是不知道这个精度模式，而是没有找到新版的计算分块、精度和输出布局组合。后续不宜将有效指导写成只传一个技术关键词。

L3P10 四人分别在约第 12、14、19、21.5 分钟认识到训练态 BN 与此前 eval 诊断不同，重复承担了语义定位成本。之后仍受深层误差累积困扰。R3 的小误差诊断没有转化为正式五次通过，晚期还转向 1×1 卷积性能优化。R2 的框架 BN 被计算回退检查拒绝；R4 试图在 CUDA wrapper 内使用 cuDNN，不符合禁止库计算的任务要求，也没有产出正确正式候选。保留这些失败，不将诊断成功当成正式正确，也不声称已出现有效的违规成绩。

纯模式也有明显的保守收尾倾向。后半程研究员频繁说“保持当前最好、只做最终确认”，自动继续后仍做局部实验；L2P71 最好值从第 17.35 分钟起没有突破。RSI 没有给优化方向，这说明过早收尾并不全由 leader 的建议造成。系统给足时间与模型是否愿意继续高价值探索，是两个不同问题。

- 新版 `7236fd54…`：初次、替换参数、内容更新均为零超阈值输出。

这项检查沿用此前 L1P77 的参数更新方式，只替换题目 reference 和参数属性名。全部研究结束后才执行，没有给模型补信息。正式 14.3 / 14.4 ms 历史保持原样，不把这份源码当作合格结果，也不事后换成别人的候选来改写正式成绩。这是模型产物和现有评测覆盖的缺口，不是本轮计时、调用或选优丢失，不以此重跑直到得到好成绩。

### 当前结论与下一步

前三题正式有两题通过最终确认，但纯模式其中一题有补充反例。唯一双方合格的 L2P71，新版探索性能为纯模式的 1.340 倍、最终为 1.311 倍；L3P10 两边失败，L1P63 的不合格纯模式结果单列。不能把这一题比值包装成七题结论。

普通后段 submit_report 的中位处理延迟约 0.66–0.77 秒，没有重现多秒级阻塞；一次报告引用错误来自把 job ID 写成 verification ID，后续工作继续。没有发现需要修复并重跑整波的共同工程故障。按计划继续 L1P77、L2P14、L3P19，再运行 L3P28，保持相同工程、Prompt、预算和评测标准。

### L1P77：独立路线的组合优化胜过本次共享

四人最终个人最好为 0.924 / 1.11 / 0.877 / 0.771 ms。R4 把活跃输出周围的零值一并写回，修正末端平面的漏写，再调整 tile，省掉大张量单独清零的开销。约第二十六分钟已经到 0.773 ms，最终获选 0.771 ms 在约第三十三分钟形成。后续边界拆分没有更好结果，领先者并非靠更多最后复测才翻盘。

获选源码 `213f793b…` 每次读取并重排当前输入和权重，IEEE 自定义卷积，没有跨调用权重缓存。同一 signed-normal 输入、普通 Parameter 替换及 `.data.copy_` 检查都通过。相比新版最终 0.834 ms，纯模式快约 7%；它说明独立探索有时能找到共享团队没有形成的组合，并不是有身份和共享就必然更好。

### L2P14：正确性提前二十分钟解决，后段收益很大

四人最终仍只有 R2 正式通过。它先从诊断确认 GEMM 的最大误差为零，问题在 hidden 归约；随后按实际版本的公开 CUDA reduction 实现调整向量化累加及 warp/lane 次序，于有效第 37.38 分钟得到首个正确候选 19.6 ms。第一次通过后，扩大 GEMM tile 等改动依次把耗时降至 6.31、5.19、4.87 ms，最后最好在第 56.60 分钟验证。

新版同题直到约第五十七分钟才首次通过 20.4 ms，几乎没有继续优化的时间。这不是两边缺少同一个概念：它们都最终实现了严格归约。差别是诊断速度、查到并正确使用具体依据的时间，以及后续能否留下完整优化窗口。身份和共享在本题没有缩短关键正确性路径，纯模式的独立 R2 反而更早完成。一次运行不能确认其概率，但不能用“新版有正确结果、goal 没有”掩盖同工程纯对照的明显优势。

最终源码 `0a63c16b…` 仍是完整 IEEE GEMM 与同一显式归约，没有经验性固定偏差。R3 的固定修正、混合结果等尝试未形成正确获选候选，不把提议写成成功的 hack。其他三人的大量 K 分块、代数化简和更高精度尝试说明，隔离也会让已经被一人解决的错误定位继续消耗团队资源。

### L3P19：重复定位的成本存在，但解释必须对上实际源码

最终个人最好为 1.95 / 1.76 / 2.02 / 2.46 ms。多名研究员最初按推理态折叠 BN，随后分别纠正；R4 到约第二十一分钟才认识到训练态差异，约第二十八分钟首次正式通过，后段仍在补做统计并行与融合。这个过程和此前纯 L3P10 类似，确实重复花了时间。

需要修正中期记录的一个因果解释：R2 的公开进度提到 NHWC，也保留了相关函数，但最终获选 `8a875e5b…` 的 forward 实际调用 NCHW 辅助函数。因此不能把最终 1.76 ms 简单归因于 NHWC。R1 则主动撤回十七个认为缺少 BN 状态处理的早期候选，十七条都已完整存储；后续最好 1.95 ms。系统没有把这些已撤回候选重新选回。

最终源码的训练 BN 不更新运行统计或计数。对 goal 搜索、goal 最终、新版和纯模式四份精确源码做同一训练、状态检查、再切换 eval 的测试：四份训练态输出均通过，但全部遗漏二十七个 BN 计数更新。goal 和新版的运行统计及切换后的输出通过；纯模式有 21,845 个统计值超阈值，切换后的输出有 9,910 个超阈值，最大误差 0.0289984。这个额外状态检查超出了原正式训练态前向评测的覆盖，故保留原成绩，单列状态语义缺陷；不能将任何一份称为完整模块状态等价，也不事后改选。`qualified` 耗时汇总只排除已知输入/参数输出反例，不能理解为全面语义认证。

### 工程与行为

这波三题没有持续 API、计时或工具阻塞。普通后段工具中位数约 0.5–1.1 秒；两次汇报引用错误来自不合法 references，并未阻断研究。RSI 仅观察、等待和监督，未给技术建议、共享同伴内容或加载身份。纯模式自身仍有提前“冻结最好、只做核对”的倾向，尤其 L1P77 后段反复汇报；同时 L2P14 的领先者能继续做出约四倍性能改进，不能把所有后半程都视为无效。

本波保持冻结配方完成，未因单题低分或研究员语义遗漏重跑。审查和所有补充作业结束后，按计划执行最后的 L3P28；七题总体比较仍需等待最后一题。

### 路线差异

四人均较早识别出 `batch_first=False`，却直到结束都没有形成新版的 CLS 依赖化简，而是在完整 patch 和 Transformer 路径上优化。R1 约第五分钟就通过完整自定义实现，后续优化到 2.51 ms；R2 首轮生成较长，约第十三分钟才通过，但独立发现连续转置权重的收益，从 3.58 到 1.85 ms，随后成为领先者。早期落后不等于路线没价值。

R2、R3 各自先每次转置当前权重，再加入对象 ID / 版本缓存，最后分别通过不同线性层的 tile 调整到 1.13 / 1.32 ms。R2 在约第四十六分钟宣布“已完成、等待系统复测”，系统继续提示使它又尝试 BM64→BM32，才获得 1.13 ms。监督机制确实避免了过早终止；与此同时，缓存的语义缺口也被两个独立研究员重复引入。

R4 在已有正确 Triton 后花了约二十分钟尝试包装 cuBLAS，违反任务的计算限制，数值上也一直失败。后来恢复 Triton，保留的库函数定义没有在通过候选的执行路径调用。CUDA Graph 方案只有 4/5 校验通过，也未成为正确候选。最后靠较小 GEMM tile 到 2.38 ms。这些失败影响了它的有效探索，但没有污染最终获选源码的计算路径。

最后十分钟报告增多，一共 91 条，包含自动续跑后的重复收尾。普通后段工具延迟没有出现旧有的持续多秒阻塞；一次 submit_report 引用错误没有阻断后续工作。没有共同工程故障需要重跑。

### 获选源码的参数内容更新反例

结束后，对 goal 的探索源码 `e06b0023…`、goal 最终源码 `0522f721…`、新版 `b4fb173c…` 和纯模式 `18bce48c…` 运行同一参数检查，更新的是 `mlp_head[0].weight`。纯模式用对象 ID 和 `_version` 判断缓存是否失效，普通 Parameter 替换通过；但 `.data.copy_` 内容更新后 ID 和版本不变，仍使用旧权重，最大误差 0.468878，20 个输出全部超出容差。另三份源码的初次、参数替换、内容更新均通过。

因此保留 1.13 / 1.19 ms 的正式记录，同时把这份已知参数输出反例从相应性能平均中排除，不事后改选一份更慢源码来重写结果。这与 L1P63 的处理一致，也不把普通参数替换已通过的事实隐去。全部四个补充作业已结束。证据：`parameter-replacement-audit-l3p28/results.json`。
