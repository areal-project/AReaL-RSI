# 从现象形成可验证的解释

先描述数据，再给解释。高寄存器数、某种 stall 占比高、低 occupancy 都只是线索，
不能单独证明瓶颈。下面是可选的判断方式，不是要求逐项完成的检查表。

| 观察 | 可能的解释 | 有区分度的下一步 |
| --- | --- | --- |
| 大量短 kernel，时间线间隙明显 | launch、同步或 host 工作占比较高 | 在语义和规则允许下减少一次中间调用，比较完整耗时 |
| 大量复制、转置或临时张量 | 数据组织消耗超过计算收益 | 比较直接读写目标布局与显式重排，计入所有转换 |
| SM 与 DRAM 吞吐都不高 | 并行工作不足、依赖等待、访存延迟或地址计算 | 结合 grid 大小、发射情况、访问模式和编译资源进一步区分 |
| 某一级访存接近饱和 | 数据量或访问效率限制 | 估算字节数，检查重复读取、复用、合并访问和中间写回 |
| tile 增大后反而变慢 | 寄存器、共享内存、尾块浪费或并行度下降 | 比较资源和 grid 变化，保留算术路径而减小 tile |
| 增加流水线 stage 没有收益 | 等待已被隐藏，或资源/同步代价超过收益 | 比较寄存器、共享内存与时间，判断是否应该简化流水线 |

## 计算量和流量

按真正执行的算法估算工作量。矩阵乘可用约 2MNK FLOP 作为起点，但 padding、重复计算、
额外归约和地址计算不会凭空消失。计算峰值要匹配数据类型、指令类型和硬件，不能用
低精度 Tensor Core 峰值去评价另一条运算路径。

先估算一次必须读写的字节数，再考虑临时数据和重复读取。这个估算不是硬件实际流量：
缓存命中、访问不合并和重放都会改变 DRAM 或缓存层流量。用“逻辑字节数 / 时间”得到的
有效带宽，不能直接作为 DRAM 利用率，也不能在低带宽时就排除访存延迟问题。

把 FLOP / byte 作为粗略算术强度，与匹配的计算和带宽能力比较，有助于选择假设；
不要把粗略 roofline 当成精确运行时间预测。小工作负载、串行依赖和同步常常落在两条上限之下。

## 资源和并行度

查看每个 program/block 的工作量与 grid 数量。总工作块很少，或尾部只剩少量块时，
即使单块高效也可能不能利用所有 SM。拆分更多工作可能增加归约和中间流量，收益要整体测量。

寄存器或共享内存增长可能减少驻留块数，但高 occupancy 不是独立优化目标；过度压缩
每块工作也可能降低复用、增加指令和 launch 成本。用实际延迟验证资源与吞吐的取舍。
编译器报告 spill 时，检查对应内存指令与时间变化，不要把更少寄存器自动解释为更快。

## 地址计算、访存与等待

连续访问同样数量的数据通常比散乱访问更容易利用事务，但连续性要看线程到地址的映射，
不能只看 tensor 名称或 shape。检查 stride、mask、边界处理、循环中的索引分解，以及同一数据
是否被很多块反复加载。预打包可能减少索引计算，也可能引入昂贵转换，必须计入完整调用。

调参多次没有稳定收益时，考虑是否需要改变计算组织、数据复用或依赖链，而非继续扫参数。
若要验证数值路径，按本题规则独立检查正确性和误差；profiling 不赋予修改容差、删减计算、
复用预存答案或绕过评测的权限。

硬件计数器的含义和限制参见 [Nsight Compute Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html)。
