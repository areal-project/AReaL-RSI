协作组并非一直没有进展；它更早得到快速实现，随后修复了额外诊断发现的数值范围缺口。

1. 约第 10 分钟，R3 的 BF16 三乘积版本正式 5/5、0.333 ms。R4 的 FP16 三乘积为 0.335 ms。

3. 第 24–29 分钟，R2 发现 `x=1e-38, w=1e37, bias=0` 的具体反例。
   原始记录中 reference 为 3.5999975，BF16 六项为 3.6036260，默认 TF32x3 为 3.5994921，
   均不满足诊断的 `atol=rtol=1e-4`。Leader 向另外三人连续转发反例、撤回要求和 IEEE 修复方案。
   四人随后都增加了每次 forward 的范围检查和自定义 IEEE 慢路径。
4. 后续继续检查非连续输入、权重、bias，以及其他 K/divisor 的支持范围。四人的工作重心
   越来越接近：保护快路径、修复慢路径、降低扫描与空 kernel 开销，然后再优化性能。

## 不能直接认定 pass@4 得到同等稳健但更快的解法

读取冻结候选源码后，pass@4 的 0.296 ms 最好版本仍是不带范围保护的 BF16 三乘积。
协作组早期也得到过这种快速方案，但发现放大输入的问题后撤回。纯 pass@4 的其他研究员也
自行发现并撤回过 BF16 三乘积的反例，但隔离机制使领先 R4 没有收到这些信息。

因此两边最终选择的数值处理方式及额外验证覆盖范围不同。没有用相同补充测试实际重跑这份
冻结源码，不能宣称该候选已经被证明不正确，也不能把它的正式 5/5 推广成所有边界都正确。
更不能为了分数恢复已确认有问题的候选。正式成绩保留原样，稳健性结论需要同条件检查。

## 工程修复这次确实改善了吞吐

约 53 分钟时，各研究员输出约 5.0–5.6 万 token；原生日志中请求开始到响应头的平均时间：

- pass@4：2.37–2.61 秒；
- v0.2.1：2.53–2.82 秒。

上轮修复前四人为 19.8–21.1 秒。当前两个 L2P71 的原生 HTTP 日志没有失败记录，计时中
API 故障为 0，GPU 排队每人仅约 11–13 秒。两组工具阻塞时间接近。现有证据不支持把本轮
成绩差异主要归因于 API 拥塞、GPU 排队或刚改的传输隔离。也不意味着已经证明系统没有其他 bug。

## 判断与后续方向

这次主要不是“先进算法被错误否定”，而是协作放大了正确性审查的范围与工作量：
有效经验得到传播，审查负担也传播给全队。精度和范围缺口有真实证据；leader 的问题在于
没有明确控制验证任务的边界、复用方式和预算，让独立探索逐渐变成四份相近的加固工作。

任务适配层应明确本题需要支持的形状、参数、数值域和误差标准，并提供统一补充验证；
不要让 leader 临时决定是否要覆盖一个通用 Conv2d 库的全部情况。RSI 层则应让 leader
区分“已确认、影响本任务的缺陷”与“可选的额外稳健性检查”，集中核实可共用证据、减少重复
诊断，并保留性能探索的连续性。发现本任务范围内的真实错误仍必须修复。
