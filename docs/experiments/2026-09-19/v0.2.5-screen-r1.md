# v0.2.5-screen-r1：限制传播没有带来稳定收益

三题均已完成探索与一次 seed 137 最终确认，worker 已退出。**本版不晋级，下一版从 v0.2.4 独立出发。** L3P10 比 v0.2.4 多得到一个正确解，但直到个人有效时间 59.85 分钟才通过，几乎没有性能优化时间；两道 L2P71 也没有形成足以支持复测晋级的整体改善。

## 限额实际做到了什么

三题登记的经验数量为 3 / 5 / 5，发送次数为 3 / 5 / 6。登记身份及父经验的接收者审计没有越额，L3 有一次沿用原 ID 的补充。原始引用也没有被 leader 发给多个新增接收者。leader 的技术建议实际发送 13 / 21 / 21 次，比 v0.2.4 的 31 / 32 / 31 次少，但输出 token 仍为约 43.6k / 44.6k / 38.9k；消息少不等于协调成本同比下降。

传播范围也确实影响了选择：L3 leader 在 17:13:30Z 明确拒绝向 R2 再转发已经给 R3 的小尺寸 BN 经验；Astra L2 则没有向第三人传播已验证的 BF16 相消反例。因此不能说限额只是写在 prompt 中。

但**总体信息流没有被限制为每条经验一名接收者**。Sol R3 在约第 15 分钟主动列出报告、读取 R4 候选并组合 K8 尾部外积，取得约 0.605 ms；R1 在约第 30 分钟也主动读取同一来源，随后正式验证 0.618 ms。两位新接收者都实际使用了该经验。本版明确保留了同 run 按需读取，因此这是机制边界，而非登记发送检查失效。显式 peer-read 尝试数为 0 / 7 / 0，团队目录查询为 2 / 7 / 0。

来源图也不能代替语义审计：L3 的 R2→R3→R1 连线并非一次已知的转述绕过。R3 分享给 R1 的中间卷积结论早于它收到 R2 的首层修复建议，且 R3 明确报告尚未采用该修复。

## L3P10：leader 帮助了突破，但合流太晚

四人首版再次独立选择相近的大路线，仍在训练态的微小舍入差异上失败。限额没有改变这种初始趋同。中段逐步排除卷积、大多数小尺寸 BN 的问题，却长时间停留在两遍归约的不同实现上。

关键链条：

1. R4 某次 Welford 实现较差，leader 在建议中也引用“Welford 更差”，随后探索缩放位置。这不等于永久禁用该方向，但反映了容易把具体实现结果外推为方向判断的问题。
2. 缩放假设被反证后，leader 于 17:24:59Z 建议构造稀疏相消输入辨别线程分组，于 17:28:58Z 给出具体的区分性 probe。R4 17:31:29Z 报告采用这一思路发现普通求和解释不了的结果，转回在线统计。
3. **17:35:45Z，R4 报告首层 mean/inv/output 全部逐位一致。** 它找到了 lane 内 Welford、跨 lane 加权合并及方差缩放/epsilon 的 FMA 组合。完整候选仍失败，不能把局部结论当成整题通过。
4. leader 17:37 开始取得新状态，期间还读取 R3、R4 轨迹和执行目录，17:40:18 才读取关键 stdout；17:41:22 将核实后的经验发送给 R1，距离原报告约 **5 分 37 秒**。R1 此前也用稀疏 probe 独立怀疑在线统计，因此接收对象有依据。
5. R1 结合自己的小尺寸精确实现及大尺寸映射继续修正，在个人有效时间 **59.85 分钟**首次整题正式正确，仅剩十余秒。最终为 20 ms。对照 R3 在 **45.78 分钟**首次正确，还能用约 14 分钟改进后段卷积，最终 8.90 ms。

这里有正面的 leader 贡献：有区分力的实验问题帮助推翻了错误假设，定向分享也参与了最终组合。但经验变成完整正确解的时间太晚。仅数“正确人数”或“消息到达”看不到这个差异。还需要区分：局部事实是否足以支持合流，谁最适合立即实施，以及关键新证据是否优先处理。

不能把 5 分 37 秒全部算成消息传输故障。轨迹中有正常模型推理、其他记录读取和证据核实；个别 MCP 工具耗时达到数秒至十余秒，仍值得后续测量。操作侧独立 profile 中，42 文件快照冷/热都约 40 ms，带 profiler 的完整 leader 状态构建约 0.65 秒，尚不足以把数分钟延迟归咎于快照存储。没有据此贸然修改通用 Runtime 或使旧对照失去可比性。

## L2P71：保留方向，也保留了重复成本

Astra 的方向相对分散，包含手工 TF32、Gluon、Winograd、预处理布局和数值安全分支。leader 没有强迫所有人改用领先实现，也会核实负结果并撤回自己的猜测。最终探索成绩接近 pass@4，是本轮较稳定的部分。

限额也延迟了反证传播。R3 很早就在 leader 构造的相消输入上确认 BF16 三项乘积漏掉 low×low，经验只再给 R2。R1、R4 后来各自重新走过相关近似、诊断、撤回和修复；R1 一度取得 4.9051×，直到末段自行发现具体反例再撤回。限制技术路线扩散与传播正确性反证，可能不适合一刀切。此轮不能据此推断最优的例外规则，但下一版不应盲目继承硬限额。

另有一项范围扩张：R3 因其他构造参数下的尾块问题，撤回了自己明确称为“本题正确”的候选，随后做了泛化修复。它后来仍取得更快结果，没有丢失团队最好，但花掉了时间。固定形状允许专门化与完整参数语义之间的理解，应在任务规则层面澄清，不能混入通用 RSI 策略。

Sol 的问题更像局部搜索停滞。R3 在获得 tf32x3 改善后，leader 建议回到 CUDA 以保留多样性；CUDA 首版 1.47 ms，之后它又借 R4 的尾部外积回到更快的 Triton。后半程多次继续调整 stage、tile、mask、cache 和归约切分，有些人过早判断“剩余空间很窄”。这些单步并非都不合理，但没有产生 v0.2.4 中较早出现的更强精度分解与布局组合。主动同伴复用仍在发生，所以不能简单解释为“限额导致无人共享”。随机起点和模型选择差异仍是混杂因素。

## 工程与补充正确性检查

- quota 的 `_owner` 对 leader 读取的 job-output 摘录误认了读取者，未沿 job_id 找回来源。L3 一条合法建议先被拒绝，约 48 秒后补原 job 引用成功。已在隔离草稿准备修复；操作侧按实际归属回查全部成功建议，未发现因此漏登记的 peer 引用或登记越额。保留本轮，不据此声称整轮工程失效。
- Sol 一次工具调用把 references 错放进 experience，schema 拒绝后自行改正；两次 checkout 为未保存工作区保护，另有两次自身路径读取失败。L3 两次读取尚不可用输出报错。预算终止时的 native cancellation 是正常停止。
- 13/13、20/21、21/21 条指导有显式确认。Sol 未确认的那条在截止前约 2.5 分钟发送，但之后研究员只进行了原生 web 调用，没有新的 RSI 工具交付机会；原始记录未显示该消息到达模型。不能把它说成已经读到但拒绝采用，也不是已停止后仍接受新发送的问题。
- 三批的六份 L2P71 **最终选中源码**都在独立操作侧命名空间接受同一个固定形状、正常有限参数的相消检查，全部输出与参考一致。检查不计入研究员预算、不返回反馈、不重测排名或重新选优。它排除了这一个具体反例，不能证明覆盖所有 FP32 输入。记录在 `../semantic-audit/`。

## 决定

不插入 Astra 三题晋级复测：本版没有在至少两个条件改善，Sol 有明显退化，L3 虽恢复正确性但仍远低于同条件 pass@4。直接继续独立的 v0.2.6：以 v0.2.4 为 base，增加简短决策依据、连续结果和上次建议跟进；优先核查能改变下一步选择的新证据，避免把单次实现失败外推为路线失败。暂不叠加 quota，也不加入 reset。

来源归属修复在批次边界集成，属于 quota 的小修复；不改变 v0.2.6 所使用的工具或基础 prompt。是否另测主动读取限制，留待后续轨迹说明它是否仍是主要瓶颈，不能因为已有旁路就立即叠加更强隔离。
