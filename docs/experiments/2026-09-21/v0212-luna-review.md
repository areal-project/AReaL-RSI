# v0.2.1.2 Luna 实验复盘

状态：v0.2.1.2 Luna 和同工程 v0.1 Luna 各七题全部完成并审查。新版相对旧 goal 有综合收益；同工程对照正式耗时总体几乎持平，身份本身的稳定增益尚未证实。见 [完整总结](v0212-summary.md)。

## 当前结果

四名研究员各有一小时有效时间，均为 Luna/xhigh。工程和任务配置与本轮 Astra 相同；不因 Luna 的行为差异修改 Prompt。表中耗时越低越好，探索和最终独立确认分开列出。

| 题目 | Goal 首小时探索最好 | v0.2.1.2 探索最好 | v0.2.1.2 最终确认 | 当前结论 |
| --- | ---: | ---: | ---: | --- |
| L3P10 | 无正确候选 | 无正确候选 | 无正确候选 | 基础正确性困难仍未解决 |
| L2P71 | 0.402 ms | 0.391 ms | 0.399 ms | 小幅改善，尚不足以证明稳定优势 |
| L1P63 | 15.8 ms | 10.4 ms | 10.5 ms | 较明显改善 |
| L1P77 | 0.877 ms，有缓存反例 | 0.824 ms | 0.834 ms | 旧探索源码单列；新旧最终源码可比 |
| L2P14 | 无正确候选 | 20.4 ms | 20.4 ms | 有效覆盖增加，但还没有加速价值 |
| L3P19 | 1.75 ms | 1.33 ms | 1.42 ms | 最后几分钟出现明显改善 |
| L3P28 | 2.76 ms | 0.620 ms | 0.639 ms | CLS 依赖化简和后续共享融合带来明显改善 |

七题中新版六题有正确最终产物，goal 在相同首小时范围为五题。五个正式探索性能比的几何平均是 1.576；单列旧 L1P77 的已知反例后，四个可比探索对照是 1.739，四胜零负。五个可比最终产物的几何平均是 1.565，其中 L1P77 使用通过补充检查的旧最终 0.883 ms。去掉收益最大的 L3P28 后，可比探索三题仍为 1.271，可比最终四题为 1.192。

没有把两边都失败的 L3P10 算作平局，也没有为只有新版正确的 L2P14 虚构性能比。新版在这一组单次实验中相对 goal 有综合收益，但不等于统计显著，也不能把四倍尝试、工程、协作与身份的共同收益都归给身份。

## 收益来自哪些实际过程

L2P71 有清楚的接力。算法研究员将失败的通用 K64 padding 与 K64+K16 实现区分开，后者把约 0.496 ms 推进到 0.398 ms。其他人独立移植验证，执行研究员最后合并后处理，得到两次 0.391 ms。早期失败没有永久封死整个 K64 方向。

L1P63 的布局研究员提出 NHWC 输出和相应 tile，其他人复现后继续优化。旧 goal 也有 NHWC 输出，区别还包括九次 IEEE dot 与三次 tf32x3 dot、每次权重重排与直接读取原参数。因此不能把约 1.5 倍的跨轮差距全部归给“发现 NHWC”，更不能仅凭突破者的身份归因于身份 Prompt。

L1P77 展现了相互检查的价值。执行研究员发现缓存权重的更新反例，leader 查看实际源码后撤回多个更快但错误的版本。最终保留的是每次 forward 重新读取、排列当前权重的实现，正式和额外检查均通过。性能收益和正确性清理应分别评价。

L3P19 提供了保留落后者的直接理由。执行研究员长时间领先，综合研究员到后期仍只有 2.54 ms；后者继续独立探索，先到 2.06 ms，再在有效第 57 分钟合并训练 BN 的统计、更新和输出，得到 1.33 ms，成为最终赢家。这个突破发生在它已多次说“最后一次实验”之后。可以确认完整探索没有被系统提前停止，但不能把这次独立突破说成 leader 已有效统筹的结果。

L3P28 同时展现了报告缺口和共享的实际价值。综合研究员第六分钟已公开说明只计算 CLS 依赖，第十一分钟正式通过 0.744 ms，却到第 37 分钟才正式报告；leader 此前仍把完整路径的 2.62 ms 当作最好。报告到达后，leader 核对源码与作业，其他三人分别导入或重写并验证。综合研究员按照具体融合建议到 0.669 ms，布局研究员进一步融合 norm1、linear1 和 ReLU 到 0.655/0.653 ms，再经 leader 反向共享，综合研究员到 0.639 ms。执行研究员随后独立组织 kernel 并在最后一分钟将 matvec 的 K tile 改为 128，正式 0.620 ms，最终复测 0.639 ms。获选源码是 `b4fb173c…`，每次计算当前参数，没有缓存答案或库计算退路。相比只看最终四人的接近分数，原始链路更能说明谁提供了实际增量。

最后四人的正式个人最好为 0.639 / 0.653 / 0.644 / 0.620 ms。接近的分数中也有同源码复测和噪声，不把每次小幅刷新都解释为新算法。算法研究员中途调用 cuBLAS 的尝试与任务规则不符，但完整数值检查失败，后来已恢复纯 Triton；没有取得正式正确候选，不能说最终成绩由该尝试产生。

## 协作仍有哪些缺口

第一，报告不是稳定的关键发现通道。L3P10 的训练态 BN、stride 和方差修正早已写在公开进展中，却没有及时 submit_report；leader 在约第 11 到第 38 分钟缺乏实质指导，也没有查看原始轨迹。新的报告到达后链路正常，没有证据表明消息丢失。L2P14 类似，GEMM 已对齐的诊断约迟十五分钟才进入共享。

L3P28 的延迟更直接：正式正确的主要结构突破约二十六分钟没有进入 leader 认知，尽管系统已保存结果。直到第 53 分钟，leader 才又通过 get_state 主动发现执行研究员尚未报告的 0.634 ms，并核实共享。这证明现有读取能力能够解决部分信息缺口，但使用时机不稳定；不能依赖所有 researcher 自觉、及时地报告。

第二，转述仍会扩大结论范围。L2P14 某个实现的 GEMM 逐位一致，并不证明另一个研究员的 tile、累加方式和代码也一致；leader 却据此前提要求接收者固定现有 GEMM。部分研究员又把近似线程结构说成与参考归约树相同，实际代码仍使用不同的合并顺序。算法研究员到第 57 分钟才通过明确的 FP32 树得到唯一正确候选。Astra 同题约第五分钟就完成了这个关键步骤并共享，差异不能归结为 GPU 等待。

第三，问题经验的单接收者限制会阻碍已确认错误的通知。L1P77 的缓存反例已转给综合研究员后，再转给算法研究员被拒；后者仍在同类缓存上提交更快版本。leader 虽能直接撤回明确候选，但作者未及时理解原因。规则允许用已验证修复转为正向经验，实际操作没有顺畅完成。应区分“未经解决的方向性风险”和“已经有反例的具体产物错误”，而不是把所有负面信息视作同一种探索影响。

第四，提前收尾和过窄调参仍然普遍。leader 在 L1P77 第 18 分钟就说“冻结源码”，后续多题反复要求只做一个邻近配置。系统自动继续使研究员仍获得完整预算，但不少回合围绕同源码复测和低风险参数展开。消息很多，并不能证明协调有效；L3P19 的两名研究员最终仍只有 4.28 / 3.15 ms。

## 工程与正确性边界

全部 28 名研究员分别获得约 3600 秒有效时间，停止检查偏差至多约 2.31 秒。第二波仅一次约 5.7 秒 API 重试；没有广泛故障等待。个人输出多数为约 6–12 万 token，后期普通报告和指导的中位延迟仍在约一秒以内，未重现旧有的整体吞吐不足和持续多秒工具阻塞。L3P28 四人输出分别约 9.8 / 10.1 / 11.8 / 9.7 万 token，后十五分钟报告、指导中位处理时间约 0.137 / 0.165 秒。


Luna 全部七题观察到 20 次 researcher 的真实 compact：18 次直接保留完整身份 developer 消息，2 次在下一次模型输出前重新注入。审查覆盖本轮 Astra、Luna 最终选定实验的 56 名 researcher；Astra 还观察到一次 compact，同样保留完整身份。没有看到身份在已观察的 compact 时丢失；身份可用并不等于模型一定持续采用不同策略。记录见 `all-v0212-native-profile-compaction-audit.json`。

最终源码与候选快照、最终回执一致，均在作者预算截止前正式验证，所有研究远端作业已终止。L2P71 新旧 Luna 源码均通过相同的低幅输入/大权重检查。L1P77 新旧最终源码均通过相同的 signed-normal、普通 Parameter 替换和参数内容更新检查；旧探索最快源码的 `_version` 缓存则在普通参数替换后使用陈旧值，不能直接放进合格的探索平均。有限补充检查通过不等于覆盖所有输入，也不据此推断作者有作弊意图。

同工程纯对照结束后发现 L3P19 的额外状态语义问题，并对四份精确源码应用同一检查：goal 搜索、goal 最终、新版、纯模式的训练态输出都通过，但都漏了二十七个 BN 计数更新。goal 与新版正确更新运行统计，训练后切换 eval 的输出仍通过；纯模式没有更新运行统计，切换后最大误差 0.0289984。原正式评测仅检查训练态前向，因此保留成绩，单列这个超出原检查覆盖的状态问题。表中的合格耗时对照不是完整模块语义认证，也不能将缺少计数的问题只算在纯模式上。证据见 `bn-state-audit-l3p19/results.json`。

原始比较与证据在 `.rsi/passk-workbench/operator/night-0921/`，包括各阶段 `analysis/`、`final-audit.json`、`tool-latency.json`、`parameter-replacement-audit/`。所有 operator 对照仅供复盘，没有向 workload 注入其他 run 的实现或结论。

## 接下来如何判断

同工程 v0.1 Luna 七题已完成：六个正式耗时对中新版四胜两负，探索几何平均 0.9988、最终 0.9895，整体几乎持平；纯模式 L1P63、L3P28 的最终产物另有参数反例。剔除这两题后剩余四对探索平均为 0.793，不能把这个子集当作全七题排名。L2P14 的严重退化尤其值得继续分析。这个对照仍不能单独分离身份收益，后者需要同工程 v0.2.1.1 控制。本轮未追加该额外整组实验，也未恢复已暂缓的 v0.1 Astra；按此前相对 goal 的效果标准，没有触发 v0.2.1.1 条件补测。

后续最值得考虑的是让关键发现可靠进入 leader 视野、共享时保留具体实现和适用范围，以及让已确认错误能及时通知实际受影响的人。当前实验保持配方不变，先完成对照，再决定是否修改机制。
