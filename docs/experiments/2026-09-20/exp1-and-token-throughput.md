# 0920-exp-1 复盘与 token 吞吐诊断

记录时间：2026-09-20 17:15 CST。实验仍在继续，此文对新实验只报告启动与诊断事实，不提前报告最终成绩。

## 选择与已启动研究

选择 v0.2.1 作为暂定 base。在当前修复后的同一工程版本下，已启动 Astra/xhigh 的 L2P71 和 L1P63，各 4 名 researcher，每人 3600 秒有效时间，leader 随最后一名结束。另启动经用户授权的 Astra/xhigh、单 researcher、纯 pass@k 的 L2P71 计时诊断，预算相同。

全部放在已有 `0920-exp-1`，该组现在有五个研究：

- 原 v0.2.1 L3P10：`research_0920_exp1_v021_0920_151159_l3p10_astra`
- 原 v0.2.2 L3P10：`research_0920_exp1_v022_0920_151159_l3p10_astra`
- 新 v0.2.1 L1P63：`research_0920_exp2_v021_0920_164321_l1p63_astra`
- 新 v0.2.1 L2P71：`research_0920_exp2_v021_0920_164321_l2p71_astra`
- L2P71 单 researcher 诊断：`research_token_diagnostic_0920_165129_l2p71_astra_pass1`

前两道新正式实验没有修改 prompt、Runtime、转发链路或评测规则。诊断实验有独立 HTTP 观察进程；它改变了网络转发所在的进程，因此不能作为“只改变 researcher 数量”的严格成绩对照。

## v0.2.1 与 v0.2.2：本轮比较

两次共用当前工程修复、工具、消息交付、researcher prompt、固定过程 reference、有效时间及最终选优。主要变化是 leader prompt。都不启用 v0.2.4 持续观察、共享配额或 reset；都允许 leader wait。

| 指标 | v0.2.1 | v0.2.2 |
|---|---:|---:|
| 正式正确 researcher | 4/4 | 4/4 |
| 各人首个正确候选，有效分钟 | 30.49–32.03 | 25.30–28.09 |
| 搜索最佳候选 | 6.73 ms | 7.41 ms |
| 最终独立复测 | 6.72 ms | 7.46 ms |
| 最终 speedup | 1.4554× | 1.3137× |
| Leader 输出 token，含推理 | 37,595 | 26,994 |
| Leader 读取轨迹 / 候选文件 | 22 / 14 | 10 / 7 |
| 指导调用 | 37（36 次成功） | 43 |
| Researcher 报告 | 56 | 57 |

最终 reference 是 9.78 / 9.80 ms，差异不是 reference 漂移。v0.2.1 的候选耗时低约 9.9%。

v0.2.2 的前期诊断更合理：把卷积精度、BN 归约和统计运算顺序分开，根据反证修正判断，全员正确早约 4–5 分钟，leader token 成本也较低。它并没有全面压制不同路线，R2 的 NCHW 路线得到继续探索的机会，R3 还尝试了 CUDA Graph。

v0.2.1 的后半程出现了更具体的、有实现依据的指导。约第 45 分钟，R3 的全局 BM32 试验失败，leader 比较 R1 代码后指出：R1 只在 H≤28 的后部阶段用 BM32/BN64/BK64，前面保留 IEEE 64/64/32，权重也按 RSC 连续布局。这不是同一个实验条件。Leader 还传达了小尺寸多通道 BN 融合的证据。R3 保留自己的卷积，随后继续 BN 融合，从约 9.67 ms 到 7.14 ms，最后到 6.73 ms。不能把全部收益因果归于 leader，但这段轨迹展示了局部经验与接收者现有实现的有效结合。

v0.2.1 仍有问题：前期也猜错过误差来源；部分经验分别发给多人，仍有趋同风险；约第 45–59 分钟的推进偏慢，最后分享的一些证据留给接收者的时间很少；最后一次指导已耗尽预算的 R3，被工具正确拒绝。

v0.2.2 的后半程更多是列举可选试验、鼓励保持不同路线，较少进一步核对原始实现并适配给接收者。指导次数更多，不等于每条指导的信息量更高。另需保留一个正面行为：R3 曾出现约 6.94 ms 的 CUDA Graph 候选，leader 检查后发现缓存失效键问题，researcher 主动撤回并修复。修复后约 7.41 ms，最终 7.46 ms。不能把已撤回结果当有效成绩，也不能把这次修复视作无理干预。

因此暂时从 v0.2.1 推进，但不能凭单次结果证明它统计上优于 v0.2.2。原始分析：`.rsi/passk-workbench/operator/0920-exp-1/ANALYSIS.md` 及同目录 `analysis/`。

## Token 差距：主要是可用探索量，不是单次思考明显变弱

主要对照：0916 native goal baseline 的 L2P71 一小时，与 0919 当前工程纯 pass@4 的 L2P71。下面 researcher 取 R1，其余三人也有同方向的延迟现象。

| 原始 Codex usage / 时间 | Goal baseline | 纯 pass@4 的 R1 |
|---|---:|---:|
| 输出 token，已含推理 | 76,547 | 40,253 |
| 其中推理 token | 37,593 | 17,715 |
| 完成的模型响应 / usage 更新 | 159 | 65 |
| 平均每次输出 token | 481 | 619 |
| 平均每次推理 token | 236 | 273 |
| 外层工具阻塞时间 | 10.91 分钟 | 17.00 分钟 |
| 工具返回序列化文本总字符数 | 125,308 | 353,910 |
| 平均单次输入 token | 62,154 | 81,963 |
| 平均单次未缓存输入 token | 2,779 | 7,188 |

两边都使用原生 `functions.exec`。Runtime 中归一化后的 inner tool 次数不能当模型请求数，也不能据此认定 researcher 没有 code mode。

此前用内部 GPU shell 进程存活时间估算“工具耗时”，错误地把与模型推理重叠的后台时间也算成阻塞。这里改用原始 rollout 中最外层工具调用至工具返回的时间并集。因此推翻旧报告中“baseline 工具阻塞反而更久”的判断。

## 已复现的主要工程瓶颈：网络转发与同步状态处理共用事件循环

当前 `HttpsTunnel` 通过 `asyncio.start_server` 在调用者的事件循环中运行。工作台中的研究 engine、作业轮询、记录读取、界面数据构建也在该循环运行；其中有大量同步文件 I/O 和对象解码。多研究并行及记录增长后，转发不能及时处理连接、TLS 和数据收发。

证据分三层：

1. 历史 Codex 日志可拆分响应头前等待与响应体阶段。L2P71 R1 的 64 次后续完成响应，在收到响应头前累计花了 **1,122 秒（18.7 分钟）**；收到响应头后累计 1,395 秒，对应 40,143 个输出 token，约 **28.8 token/s**。Baseline 保留下来的 86 次网络日志中，响应头前等待中位数 **2.80 秒**，收到响应头后的输出约 **29.3 token/s**。基线日志只覆盖后部 86 次，不能直接把其累计等待与 R1 全程累计相减。
2. 同一时刻、同一模型/endpoint/key、同一原生 Codex 二进制、约 14 万输入 token、仅回答 `OK` 的合成测试：独立隔离转发进程 **6.91 秒**；经工作台正在使用的转发端口 **43.72 秒**。独立直连 custom TLS **9.24 秒**，系统 TLS 直连 **6.96 秒**。没有执行研究工具或 GPU，也没有传入任何历史解法。
3. 固定 559,341 字节的同一合成请求，用 curl 复测：工作台转发 HTTP/2 **24.42 秒**，其中 TLS 建立 **14.63 秒**；工作台转发 HTTP/1.1 **11.90 秒**，TLS **5.41 秒**；独立转发 HTTP/2 **3.42 秒**，TLS **0.21 秒**。HTTP/1.1 同样受影响，不能归因于 HTTP/2 协议本身。缓存及采样时负载不同会影响总耗时，TLS 阶段的数量级差异不由模型推理或缓存解释。

进程采样看到工作台异步线程大量执行同步文件读取、目录扫描和 JSON/对象处理。只读微基准中，读取 47 个完整 run 对象约 0.77 秒，单个 run summary 约 0.16 秒；解码还反复调用 `typing.get_type_hints`。这些具体函数的占比不是线上全程火焰图，不能把全部延迟精确分摊给某一个函数，但网络转发受同循环工作阻塞这一机制已经通过对照复现。

相关代码：

- `src/areal_rsi/modules/runtime_network.py`：转发服务运行在当前 loop。
- `src/areal_rsi/modules/runtime_package.py`：为原生 Codex 设置该 HTTPS_PROXY。
- `src/areal_rsi/research_app.py`：在工作台 loop 启动 engine；界面 list/detail 同步读取记录。
- `src/areal_rsi/coordination/engine.py`、`coordination/jobs.py`：高频 tick / poll。
- `src/areal_rsi/execution/manager.py`：每次 poll 多次加载所有 job 记录。
- `src/areal_rsi/base/storage.py`：递归 decode 中重复解析类型注解。

不能据此断言 pass@4 的所有成绩差异都由网络解释；但它确实让目前的四人各一小时不等于四份 native goal 一小时。

## 有效时间还漏掉一类底层重试

原生客户端 SQLite 日志中，R1 在完成响应对应的区间内有 **11 次底层 HTTP 请求失败**，随后自动重试。其他 L2P71 researcher 有 5–7 次，L3P10 有 7–14 次。这里只数个人截止前、完成响应区间内的失败，排除了预算停止后的报错。

这些失败没有全部成为 app-server 的 `error` 通知，Runtime 的 `api_wait_seconds` 因此仍为 0。此前“API wait=0，因此没有 API 故障”的结论不成立。当前一小时里有未扣除的重试等待。

不能把所有响应头前等待都扣除：它也包含正常传输、服务端接收/准备等。应该记录和扣除确实识别到的失败及重试间隔，另将框架自身阻塞作为性能 bug 消除，而不是用改计时掩盖。

## 第二项确定差异：GPU 与模型重叠较少，反馈较长

Baseline 常用短 `yield_time_ms` 让 GPU 命令在后台运行，再思考、编辑或取回结果。Researcher 多调用 `run_job(wait=true)`，外层 `functions.exec` 一直等结果；虽未结束原生 turn，也保留上下文，但那段时间模型不能继续工作。

R1 多阻塞约 6.1 分钟，反馈字符总量约 2.8 倍。反馈变长又加快上下文增长及缓存未命中，增加后续开销。它与转发阻塞叠加，量级足以解释 token 缺口的大部分；不需要假定 Astra 在 researcher 身份下单次就弱了一倍。

## 单 researcher 诊断的阶段性结果

17:15 时完成 35 次响应，输出 **23,807**，其中推理 **10,349**；约 **22.45 分钟有效时间**。独立观察进程中，响应头等待中位数 **1.80 秒**；工具返回到下次请求中位数 **12 毫秒**。输入增长至约 75,600 token 时，响应头等待仍约 2 秒。

这支持“常规请求之间没有十几秒的固定 Runtime sleep；关键拥堵在共享转发路径”的判断。该诊断仍在原组运行到个人一小时上限。由于观察进程本身绕开了共享 loop，不将其成绩当严格的单人/四人消融；实际因果证据主要来自同客户端、同合成输入的独立/工作台转发对照。

## 接下来应先修复什么

1. 网络转发独立运行，保留当前域名限制、TLS 验证与 run 隔离，不与研究/UI 的同步记录处理共享 loop。
2. 从高频路径移走已完成 job 和完整 run 的反复读取；界面只读工作不阻塞模型网络；缓存稳定类型注解等已知重复计算。具体优化根据热点做，不扩大重构。
3. 覆盖 native HTTP 底层重试的计时，区分正常推理、已确认重试和本地事件循环堵塞。
4. 缩短 GPU 工具单次等待，保留原 job ID 后继续取结果，允许模型在期间做独立工作；默认反馈只返回结果与引用，细节按需读取。评测严谨性不变。
5. 再以修复后的纯 pass@1 / pass@4 检查同时间的模型吞吐及成绩，再推进 leader 策略消融。

本轮未热改正式实验、未重启工作台。分析脚本、metadata 日志、合成传输对照与进程采样在 `.rsi/passk-workbench/operator/token-diagnostic-0920/`。观察器不存储请求正文、生成文本、原始推理或凭据；合成探针工作区只含自行构造的测试文本。相关 Codex 请求构建行为亦核对了 [0.153.4 官方实现](https://github.com/openai/codex/blob/rust-v0.153.4/codex-rs/core/src/client.rs)，但本报告的瓶颈结论以本地测量为依据。
