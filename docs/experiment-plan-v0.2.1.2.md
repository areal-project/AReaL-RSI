# v0.2.1.2 身份差异实验计划

制定时间：2026-09-20 晚至 09-21。状态：执行完成。新版 Astra 七题、新版 Luna 七题、同工程 v0.1 Luna 七题，共二十一个研究全部完成并审查；另保留中止和无效旧轮次。每人有效预算、源码对应、分组与全局并发检查完成。总报告见 [v0.2.1.2 实验总结](experiments/2026-09-21/v0212-summary.md)，详细记录见 [执行过程](experiment-progress-v0.2.1.2.md)。
最终判断：当前版本相对 goal 满足本轮约定的综合收益标准，因此完成了 Luna 泛化，没有触发 v0.2.1.1 条件补测。同工程 Luna 新旧模式的正式耗时总体几乎持平，身份本身的稳定增益仍未证明。参数缓存反例与额外模块状态问题单列，历史成绩不改写。
最新调整：暂缓 v0.1 Astra 重测，保留 v0.1 Luna 七题重测，减轻本轮实验负担。
效果标准补充：可与 v0.2.1.1、已有 v0.1 或 goal baseline 比较；不要求稳定胜过 v0.2.1.1，但综合来看必须相对同模型 goal baseline 有明显优势，允许部分题目不领先。

## 目标与范围

在 v0.2.1.1 协作机制上，为四名独立 researcher 配置一名通用综合研究员和三种 KernelBench 研究偏好。
检验它们能否减少重复探索、保留不同路线，同时通过现有定向共享提高团队最好结果。
身份不同、搜索词不同或分数接近本身都不是成功标准。

先修复[工程待办](engineering-backlog-v0.2.1.1.md)，再实施身份配置；不同时加入 reset、投票或新的 leader 搜索策略。
所有修复同样适用于 v0.1。历史成绩与失败记录保持原样。

## 固定条件

- 七题：L3P10、L2P71、L1P63、L1P77、L2P14、L3P19、L3P28；所有阶段排除 L2P80。
- 每题固定四名 researcher，每人 3600 秒有效时间，不限提交次数，不设分数提前停止目标。L3P10 同样执行一小时预算。
- leader 与 researcher 使用同一模型，Astra 为 gpt-6-astra，Luna 为 gpt-5.6-luna，均为 xhigh。
- leader 随最后一名 researcher 结束，之后系统完成最终确认。正常推理、编译和 GPU 执行计时，已识别 API 故障与 GPU 排队按现有口径扣时，重叠只扣一次。
- 保持当前 Codex → AReaL Agent Runtime、原生 CLI、原生搜索、API 配置和 et15 GPU 排队服务。模型只读当前 run 的授权材料。
- 保持固定探索 reference、相同正确性与数值要求、正式最佳有效候选一次独立最终复测。补充测试的解释对所有身份和模式一致。
- 全局最多三题同时运行，Astra 与 Luna 合计计数；探索和最终确认都占位。停止的研究须确认后台 GPU 作业终止后才能释放位置。
- 每波完成最终确认和简短轨迹审查后，再启动下一波。不按固定整点盲目追加任务。

## 先修复工程问题

1. 对明确候选 ID 列表实施原子批量撤回；已受理撤回必须在最终选优之前完成，避免研究预算结束截断清理。是否需要独立待核实状态，按现有候选状态机制决定，不引入自然语言状态推断。
2. 对后期普通工具变慢分段计时，区分请求排队、处理、状态构建和写盘，定位并修复主要原因。用已有长轨迹做短回放检查，不先启动一小时实验定位。
3. 诊断脚本落为真实 Python 文件执行，使 @triton.jit 可以找到函数源码；保留参数、精度与 run 隔离。
4. 核对与 goal baseline 的任务契约：数值域、误差阈值、合法实现和补充诊断解释。不能为提高新模式成绩放松要求；若发现实质差异，统一任务配置并标明旧对照不可直接比较。

只做有针对性的验证：撤回与结束同时发生、包含 JIT 的真实诊断、长历史下工具耗时，以及身份在恢复/compact 后保留。
准备完成后冻结工程版本，更新工作台；不热改正在运行的研究。

## v0.2.1.2 的身份设计

底层仍为 v0.2.1.1：完整独立探索、非阻塞报告和建议、同 run 证据查看、问题经验限一名新增接收者、已验证正向经验可定向分享给多人。
v0.2.1.2 作为新的可选版本，旧版本仍可原样选择。通用能力只负责加载和保存身份，GPU 知识属于 KernelBench 配置。

| 槽位 | 身份 | 范围 | 主要偏好 |
| --- | --- | --- | --- |
| 1 | 综合研究员 | 通用 | 从实际任务和测量自由选择方法，不绑定 GPU 或某种技术 |
| 2 | 算法与计算结构研究员 | KernelBench | 数学变换、计算组织、不同算法及完整实现成本 |
| 3 | 数据布局与访存研究员 | KernelBench | 数据搬运、布局、复用、中间结果与完整执行成本 |
| 4 | GPU 执行与编译研究员 | KernelBench | 线程组织、寄存器、共享内存、指令和加载/计算流水线 |

通用身份约 150–250 汉字，三个专门身份各约 350–600 汉字，分为几段自然语言。
每份写清研究习惯、优先观察的信息、调研偏好、如何用实验检验，以及何时放弃不适用的偏好。
不指定题目的已知解法，不引入其他 run 的发现，不设固定算法，不让人只分析或只写代码。
四人都必须完成调研、实现、正确性验证和性能改进，遵守同一评测标准。

身份以版本化 Markdown 保存，使用现有统一加载器。在公共角色开场后、协作及工具说明之前插入本人的完整身份。
身份属于稳定指令，启动、继续与会话恢复均从冻结配置装配，不仅存在于第一条任务消息。
在现有 compact/恢复状态中保留身份 ID 和一句研究偏好，重建上下文时恢复完整指令；需要核验 Runtime 实际接收内容。
不定时灌入长提醒，不要求 researcher 反复宣读身份。若提供 AGENTS.md，它与固定指令使用同一来源，不维护两份独立内容。

启动时固定四个槽位，记录身份文件和实际 Prompt 指纹。leader 能看到每人的身份与实际进展；工作台研究员卡片显示身份名称。
leader 仍依据证据提供帮助，不能按身份强行锁定路线。身份只是偏好，允许有依据的方向变更。
v0.1 重测使用四份相同的原有通用 Prompt，不加载这三个专门身份，也不启用经验共享。

## 顺序与工作台分组

逻辑组按版本、模型和目的区分；七题可在同一组内分波启动，不为每波重复建立七题组。
研究名称包含题目、模型和版本；重跑追加 r2 等标记，原研究保留并记录中止原因。

| 阶段 | 工作台组名 | 题目和启动方式 | 条件 |
| --- | --- | --- | --- |
| A | v0.2.1.2-astra-初测 | L3P10、L2P71、L1P63，三题并行 | 修复和启动前验证完成 |
| B | v0.2.1.2-astra-扩展 | L1P77、L2P14、L3P19，随后 L3P28 | 初测有效、效果有希望 |
| C | v0.2.1.2-astra-复测 | 有收益但证据不足的关键题，最多三题同时运行 | 需要确认而非直接推广 |
| D | v0.2.1.2-luna | 全部七题，按前三题、另三题、最后一题启动 | 现有可比对照、轨迹及必要复测足以支持 Astra 有效；不足时保留不确定结论 |
| 条件补测 | v0.2.1.1（现有分组） | Astra / xhigh：L3P10、L1P77、L2P14，随后 L3P19、L3P28 | 仅当 v0.2.1.2 最终判断无效时，补齐该版本此前未测的五题 |
| E | v0.1-luna-工程修复后 | 全部七题，3 + 3 + 1 | 必做，独立 pass@4 |

默认完成新方法测试后执行 E，无论新方法有效与否。
v0.1 Astra 重测暂缓，不在本轮自动启动整组或少量关键题，不预建空实验组。
若新方法最终无效，先执行条件补测，再完成 E；若结论是在后续分析中才明确，则在结论明确后追加条件补测。
v0.2.1.1 已测试 Astra L2P71、L1P63，因此剩余五题按上表安排，使用共同工程修复和原版协作 Prompt，不加入新身份。新增研究加入现有 v0.2.1.1 组，不改写原两题记录。
原 L2P71 的撤回遗漏问题仍明确标记；补齐五题不意味着原分数自动变得可信。需要精确比较时再对有争议的旧题单独复测。
条件补测只在方法确实无效时触发。工程故障或结论尚不确定时先修复、诊断或有针对性复测；不为了避免负面结论反复修改到偶然获得高分。
历史 v0.1 受到工程差异影响，只能提供初筛线索。使用已有 Astra 对照时明确其工程、预算和评测差异，结合轨迹与必要的新方法复测判断；不能把工程改善全部归因于身份。
若仍缺少关键 Astra 对照、无法判断收益，记录具体缺失证据并向用户说明，不自动恢复已暂缓的实验，也不强行宣布有效后扩展 Luna。此时仍完成必做的 v0.1 Luna 七题。
若需要区分身份收益与 v0.2.1.1 已有协作收益，可针对关键题补同工程 v0.2.1.1 对照，单独分组；不默认扩成额外七题。

## 运行中检查和中止条件

启动后约 5 分钟检查四人是否完整启动、模型和身份是否正确、任务材料是否一致、工具与 GPU 是否可用。
约第 20 分钟进行第一次深入检查，随后约每 10–15 分钟检查；同时查看每人的有效时间和实际活跃时间，避免把排队误判为研究失败。
第 40–50 分钟重点看身份是否仍影响实际工作、后期工具是否变慢、建议是否带来重复审查，以及候选撤回和预算结束的衔接。

每次检查串起实际轨迹：研究问题 → 搜索/实现 → 实验 → 结论；关键共享看来源、接收、采纳动作和结果。
观察操作在系统外进行，不给研究员补其他 run 的答案，也不临时替他们制定优化路线。

遇到以下情况，及时停止受影响研究，修复并验证后从头重跑：

- 身份配置未加载、恢复后丢失、工具故障持续阻断实验、计时或候选状态错误、跨 run 隔离失效。
- leader 将四人明确改成只能完成局部工作的分工、提前叫停持续探索等，违反完整独立研究的基本设定；或其他经原始轨迹证实的严重流程偏离。
- 共用工程问题影响全部三题时停止整波；单题问题只停止该题。重跑时仍受全局三题限制。

低分、暂时无正确候选、合理采用同种算法、一次不佳建议，不单独作为中止理由。
身份完整到位却没有拉开研究方式，本身就是机制可能无效的结果，不能一律称为工程故障并反复重跑。
不删失败样本，不只保留修复后的好结果。同一故障复现时先离线定位，不反复启动昂贵研究试错。

## 每阶段分析和后续选择

每题记录正式最终成绩、探索最佳、最终选中源码的有效性、首次正确时间、每人完整最佳曲线及有效时间。
跨 run 优先比较候选耗时并同时列出 reference；不直接把 reference 漂移当作协作收益。
记录每人输出/推理 token、工具阻塞、API 故障和 GPU 排队，确保仍获得预期研究资源。
整理四条路线及其演变，查明独立突破、重复无效尝试、共享的实际收益和导致过早趋同的建议。

主要效果判断以同模型 goal baseline 为参照，v0.2.1.1 和已有 v0.1 为辅助。按候选运行时间逐题比较，并报告有效题的相对性能几何平均及胜负分布；未得到正确候选、来源或评测不一致的题单列，不从汇总中悄悄剔除。
初筛综合改善超过约 10%、不是单个异常高分掩盖多题严重退化时优先扩展；边界结果结合轨迹和独立复测判断。不要求每题都赢，也不要求稳定胜过 v0.2.1.1。
这里的明显优势是实验调度标准，不等于一次运行已证明统计显著。最终需看更广题目上对 goal baseline 的综合收益；小幅单次上涨不能直接宣称有效。
广泛推广还需看剩余题目，不能由单题突出成绩掩盖多题退化。无正确候选和不满足规则的候选单列，不能混入平均加速比。

机制正常但效果差时，先完成轨迹分析。只对有明确证据、可以小改动解决的问题做一轮有针对性的修订，例如身份被误解为硬限制、调研篇幅挤占实际实验、leader 无依据要求放弃某种偏好。
Prompt/策略修订保留原 v0.2.1.2，另存为 v0.2.1.2.1 等明确版本；工程复跑保留协作版本并记录代码指纹与 r2。
修订先重跑受影响的初筛题，不直接扩七题。若确认方法无效，则结束这条探索，补齐 v0.2.1.1 五题并完成必做的 v0.1 Luna 七题；证据不足则明确记录不确定，并在未暂缓的实验范围内进行有限的关键对照或复测后再作判断。
Luna 结果独立解释；不将 Astra 上的收益预设为 Luna 必然有效，也不为挽救 Luna 随意改动已经验证的 Astra 配方。
若 Astra 有效、Luna 无效，结论是存在模型适用范围，不将其自动归类为整个人设方法无效，也不因此触发 v0.2.1.1 的条件补测。

## 执行记录与时间预期

复用现有 batch.py 和批次配置启动；补足全局并发检查、状态记录和有条件的后续阶段安排，不另做复杂调度平台。
保存 run ID、组名、状态、代码和 Prompt 指纹、模型、预算、评测配置、每次检查记录与推进理由；重启监督后先核对已有 run，避免重复启动。
后续批次只有在前批审查结论明确后才获准启动。最终报告同时保留正面、负面、中止和复跑结果。

如果完整执行，新方法 Astra 七题 + Luna 七题 + v0.1 Luna 七题，共 21 个研究，84 个 researcher 小时，不含 leader及额外复测。
按上面的阶段分波约九波，每波至少约一小时墙钟，另加工程准备、分析、最终确认和故障等待；不能承诺一个普通夜晚内全部完成。
若初筛确认无效且无需进一步修订，三题初筛 + v0.2.1.1 五题补测 + v0.1 Luna 七题对照共 15 个研究，约六波。
实际推进以完成状态和分析结论为准，不为赶天亮缩短预算、跳过分析或突破并发上限。
