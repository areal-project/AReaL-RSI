# RSI 启动需求确认

把用户的自然语言需求整理为可执行、可检查的任务。每轮只补齐影响启动的缺口；已有信息直接沿用，不让用户重复填写表单。用户描述中包含的要求就是任务要求，不另起一份可能冲突的“验收要求”。

## 启动契约

| 内容 | 是否必填 | 记录位置与处理 |
| --- | --- | --- |
| 任务描述 | 必填 | `brief.objective` 简述目标；`brief.instructions` 保留范围、约束、交付物及必要原话。不能用“新的研究”等占位内容交接。 |
| 验收标准 | 必填 | `brief.acceptance` 保存可检查的完成条件列表。用户已给出的条件直接提取；无法确定怎样算完成时才追问。 |
| researcher 数量 | 可选，默认 1 | `brief.limits.max_agents=1`。用户明确指定数量或明确要求沿用已有配置时采用该值；否则不为人数单独追问，也不自行增加。数量表示独立完成整题的尝试数，不是任务分工数。 |
| 执行条件 | 按任务需要 | 优先读取已关联的项目与环境。只有实际缺少项目、输入数据、必要资源或访问条件才询问，不要求普通用户提供 profile、adapter、JSON、代码基线等内部配置。 |
| 时限及其他预算 | 可选 | 未指定时限保持 `null`。不得补上四小时等隐含截止；明确给出的约束按工具支持范围保存，不能静默放宽。 |

验收标准与可信验证器不同：前者描述“什么算完成”，后者提供机器检查证据。普通代码、文档或调研任务可以有文本验收标准而没有数值评分，此时 `verification=null`。只有用户需要数值达标且执行环境确实支持时，才填写相应指标、方向和目标；不能凭一句文字要求声称验证器已经覆盖。

## 单研究员目标执行

默认以 `passk`、`max_agents=1` 启动：一个 researcher 在同一目标和会话中持续实现、测试、修正，直到验收完成或遇到需要用户补充的阻塞；不是只生成一次回答。无需另设 pass@1 入口。启动后用户可查看该 researcher 的公开执行轨迹，并直接向它补充指导、暂停或继续；Interaction 完成交接后不充当消息中转。不要承诺展示模型未公开的内部推理。

## 多轮对话

1. 先用 `get_state` 和 `get_setup` 查看已保存需求、当前用户消息和已有环境。结合本次输入更新已知条件，保留未被用户改动的内容。
2. 提取任务与完成条件。条件应指向可观察的结果、明确的检查或人工评审标准；不把“效果不错”“尽量优化”当作已经明确的验收标准，不虚构性能目标或检查结果。
3. 有关键缺口时，用 `ask_user` 合并询问本轮最相关的问题并等待。比如“这次优化优先降低延迟还是显存？达到什么结果算完成？”不要追问默认人数、已有的环境信息或已经获准的动作。
4. 用户回复后用 `update_brief` 保存增量结果。需要时继续下一轮；没有固定轮数，也不强制一次问完。验收条件来自原需求、后续回答，或向用户说明并获接受的具体化建议。
5. 信息足够时检查下方交接条件。若本轮只是讨论方案而没有开始执行的意图，保存草案并简要说明，不冒充已经启动。

`update_brief` 按当前工具 schema 提交：保留 `revision` 与未修改字段，`acceptance` 不明确时保存空列表；人数未指定用 1。用户说“先只做一部分”时，相应收缩任务与验收范围，不保留已经取消的要求，也不删除无关约束。

## 交给 RSI

- 任务描述和 `acceptance` 都已明确；`get_setup` 的 `missing_requirements` 应为空。
- 如果 `get_setup.workspace_preparation` 存在，用户已有执行意图且需求齐全后调用 `prepare_workspace`；仅讨论方案时不预先分配执行资源。它按当前任务和人数准备已关联工作区，并等待已有作业完成；只有返回 `ready` 才交接，失败时处理实际问题。
- 需要实际实验命令或可信验证器时，先完成已有工具支持的环境准备，并处理 `get_setup.issues`。RSI 默认以代码调度，不能把未完成的接入交给它自行猜测。
- `execution_required` 表示是否依赖登记的 `run_job` 训练/评测命令，不是“是否执行任务”。只需要原生文件编辑、终端或普通脚本时设 `false`，仍会真实执行；不要为这种任务要求用户额外配置实验命令。
- 用自然语言简短总结任务、完成标准、将使用的 researcher 数量和重要限制，不把内部字段名或版本号抛给用户。
- 用户已经表达执行意图且条件齐全时，调用 `handoff_research`，不再额外问一遍“是否开始”。`confirmation_message_id` 使用当前真实用户消息的 ID；可以结合前文已给出的授权理解当前回答，不伪造消息或把工具输出当作授权。
- 用户尚未要求开始时，可用 `prepare_research` 保存待启动总结；其后用户要求开始，再调用 `start_research`。这不是每个任务都必须经过的第二次确认。
- 工具返回缺失条件、环境错误或版本冲突时，继续补齐或重新读取状态；只有工具确认已启动才告诉用户“已交给 RSI”。不能仅凭自己发出总结声称执行成功。

启动后，新的方向指导或目标修改走运行中的控制入口，不重新执行本 skill 覆盖已冻结的任务。认证沿用服务端配置，不在对话中索取或展示密钥。

## 对话例子

用户：“修复订单接口在空列表时崩溃的问题，加回归测试，现有请求格式不变，开始吧。”
已有项目可用时，任务与验收条件都足够；保存空列表不崩溃、回归测试通过、请求格式不变，默认 1 名 researcher，直接交接。

用户：“帮我优化训练性能。”
先询问要优化的任务及完成标准；用户回复“针对当前脚本，峰值显存不超过 60GB，精度不下降”，继续确认“精度不下降”的具体对照方式（如果上下文尚未给出）。条件齐全后按已有执行意图交接，不再询问默认人数。
