# 延迟、消息时序与研究质量

这次只分析已有记录，没有启动研究或修改运行代码。检查范围是 9 月 21 日凌晨到晚间的 38 个 Luna 研究、152 名 researcher，包含旧 v0.2.1.2、旧纯 pass@4、v0.2.1.3、v0.2.1.4 和晚间复测。

**已确认正常响应变慢、部分交流变慢，也有故障改变团队协作时序的直接案例。但还不能把相同有效时间、甚至相近输出量下的全部分差归因于 API 延迟。**

## 统计口径

- 响应收尾间隔：原生 rollout 中一次响应最后一个模型输出 item 到该次 token_usage_record 的时间。不是纯服务端推理或网络时间，可能与工具执行重叠。
- 消息送达：消息创建到接收者原生输入中首次出现完整消息正文的间隔。正文通过 user message 或 RSI 工具返回进入上下文，不等于模型已经理解、接受或执行。
- acknowledge_messages 是模型确认动作。它可能晚于实际送达，不能当作首次阅读时间。旧组也出现很晚才确认的消息。
- 起始一分钟内的 leader 任务消息不计入后续建议。报告消息包含 submit_report 和回合结束时自动形成的报告，不把每条报告都当成独立突破。
- 少数消息未能在原生输入中匹配，不能直接判为丢失。下表列明样本量；不同版本、时段和并发数均存在混杂，广泛出现不等于已证明因果。

| 08:30–10:48，旧 pass@4 七题 | 28 | 0.21 |
| 15:11，v0.2.1.3 七题并发 | 28 | 0.24 |
| 17:42，v0.2.1.4 七题并发 | 28 | 2.87 |

早晨两个批次全部 56 名 researcher 的个人中位数不超过 0.23 秒，最新十二人明显进入数秒级。这不是只发生在某个 R3 或某个 prompt 上的现象。降低为三题并发后也未恢复，但各批次时段不同，不能据此证明并发完全无影响。

另一方面，v0.2.1.3 时收尾间隔仍接近旧版。不能用后来出现的这个特定延迟现象解释所有早期版本退化；也不能因此排除它当时存在其他请求阶段的延迟。

定位到哪里、尚未定位到哪里，见 [响应时序报告](0921-exp-2-timing-and-style.md)。目前只能称为原生响应链路的端到端延迟，不能唯一归因于上游 API。

最新组建议最长送达 78.1 秒，未发现普遍几分钟的积压。一个 454.5 秒的确认延迟，对应正文其实在 67.5 秒时已进入上下文，因此不能写成“等了七分半才读到”。

最新组 researcher 报告显著减少，但 leader 建议数量没有减少；leader 完成模型响应从 288 次降为 116 次。这说明观察与干预的比例发生了变化，不能只说交流总量少了。它并不自动证明每条建议质量下降，也不能把旧版重复报告全部算作有价值探索。

当前 Codex 消息递送方式：运行中的 agent 在 RSI MCP 工具返回时接收 incoming_messages；空闲时消息可以启动下一回合。原生 exec_command、apply_patch、kb 命令本身不会自动附带 RSI 收件箱。非阻塞表示发送方可以继续，不表示接收方在任意一次原生模型调用前都会立即收到消息。

对应实现为 `src/areal_rsi/modules/research_runtime.py` 的工具结果包装和 `src/areal_rsi/coordination/engine.py` 的 incoming_messages 回调。延迟可能来自当前请求/工具、下一次 RSI 调用的时机和 leader 核查过程；只有消息创建时间不能区分这些部分。

## 一个明确超出“少了有效时间”的案例

19:42 的 v0.2.1.2 对照 `research_batch_35c0064966644a0f_1_l2p71`，R3 的模型连接卡住约四十分钟。替换转发进程后，同一模型会话恢复，计时账本自动扣除 2395 秒。详见 [故障记录](https-stall-incident.md)。

从研究启动算起：

- 第 6.27 分钟，leader 给 R3 发送 1.30 ms 的团队方案。
- 第 9.77–40.54 分钟继续发出九条更新，方案从 1.07 ms 演进到 0.621 ms。
- 第 45.49 分钟，十条积压消息在同一个工具返回中一起进入 R3 上下文。
- 第 46.41 分钟，R3 公开表示采用团队的 0.621 ms 结构，只验证一个缓存/访问改动。
- 第 47.16 分钟，leader 又依据 R3 的首版 5.20 ms，要求它转向团队的 0.601 ms 方案；第 49.07 分钟明确要求停止原分支。

R3 正文表明它采用的是最新方案，没有证据显示它把十条旧建议逐个执行。实际受损的是参与时机：它的独立初始路线尚未充分迭代，团队已经形成成熟方案，恢复后它转为跟随。返还其个人时间不会让其他三人重新经历一遍开局，也无法恢复它本可能对团队早期选择产生的影响。

这是“故障改变信息到达顺序和团队相对进度”的直接证据。该研究后来被中止，不能拿它的最终成绩冒充完整等有效时间对照；也不能据此估计所有其他研究受影响的幅度。

## 但吞吐与协作时序仍不能完整解释分差

现有有效时间只扣除 API 故障/重试、GPU 排队。正常但变慢的模型请求仍计时，因此同样 60 分钟并不意味着同样多的探索轮次。不过，已有更强的数量归一化证据：

- 旧 pass@4 的 R1 在 23,962 输出 token 时已得到 0.524 ms；最新四人各完成约五到六万输出 token，最好仍只有 0.649 ms。
- goal baseline 在不超过新赢家 60,650 输出 token 的前缀中已达到 0.471 ms，新赢家只有 0.649 ms。
- 新 pass@4 没有 leader 技术建议或跨研究员分享，因此不能把这部分退化解释为协作消息迟到。
- 新 R1 改动未被 ModelNew.forward 调用的函数，却据原有实现的测量断言 tf32x3 没有收益。这个实验推断错误有冻结源码证明，不能由消息队列延迟直接解释。

另外，旧 v0.2.1.2 的正确 TF32x3 经验在第 5.83 分钟报告，第 7.15 分钟分享，第 7.21 分钟进入 R4 上下文；R4 继续独立移植并在第 13.48 分钟报告 0.497 ms。最新组第 8.81 分钟报告 0.752 ms 权重布局成果，第 11.06 分钟分享，第 11.26 分钟进入 R3 上下文。最新组并不是完全没有及时、有效的信息共享；更大的区别在于发现和共享了哪条技术路线。

输出 token 也不等于相同研究工作量，更不是相同隐藏计算量。这些比较证明“只是少输出一些”不足以完整解释已有结果，但不能仅凭它们判定服务端模型质量下降。时间压力改变选择、故障改变上下文/相对进度、采样路径和上游执行条件等，还没有被受控实验分别隔离。

## 下一步怎样区分原因

先解决已有证据指向的链路异常和失败请求计时，不继续叠加 prompt 变更。之后最有区分力的是同一时段的受控延迟对照：保持模型、prompt、工具和交互预算相同，分别比较单 researcher 与协作组，在一侧人为加入已知延迟，并记录发现、报告、leader 建议、正文送达、接收者下一次实验的完整时序。

如果延迟只减少单位时间轮次，在近似相同交互预算下差距应显著缩小；若仅协作组仍受损，且可看到信息顺序、方向切换和重复工作变化，才能更有力地归因于协作。需要重复样本，不能靠一次得分判断。当前未启动这项实验。
