# 工程修复与 Astra L2P71 单人 / 四人对照

2026-09-20。三项研究自然结束后，17:54 将修复部署到本地 8198，进程 9854。
`0920-exp-1` 的五个研究及分组保持原样。本次没有改 leader/researcher prompt、研究策略或评测规则，也没有改写历史成绩。

## 修复内容

1. HTTPS 转发改为独立子进程，避免工作台事件循环中的同步文件操作拖慢 TLS 与数据收发。
   保留公开地址限制、DNS 地址固定和端到端 TLS；父进程退出时，子进程通过 stdin EOF 退出。
2. 工作台 list/detail 在工作线程中读取独立的持久化视图；不在后台线程操作正在运行的 coordinator。
   缓存稳定的类型注解，以及文件版本未变化的作业记录；完成作业的排队回执每次恢复后只读取一次。
3. Runtime 补充原生 HTTP 内部重试事件。首次失败请求的起点到重试成功响应头计入故障区间；
   与既有流式故障、GPU 排队取并集。正常请求延迟继续计时。
   原生 HTTP 状态从 stderr 即时提取，只传时间与状态，不保存原始行、URL、响应头或凭据。
   没有改 Codex 模型循环、历史、工具、compact 或重试行为。
4. 连续研究的 GPU 工具单次等待上限从 240 秒降到 10 秒。作业未结束就带原 ID 返回，
   researcher 可以继续独立工作，之后取回同一作业结果。直接返回的反馈正文限制为 3000 字符；
   验证结果保留，详细反馈仍通过原记录引用或输出文件读取。

这些改动属于通用 Runtime、执行和工作台模块，没有放入 KernelBench 专用逻辑。
Runtime 固定为 `0.4.0.dev1+rsi2`，patch、重建脚本、wheel、摘要与 lock 已同步。

验证：54 项相关测试通过；2 项需要显式安装原生 DSH 的测试按原条件跳过。
Ruff、格式检查、mypy 和 diff whitespace 检查通过。回归测试覆盖父事件循环完全阻塞时转发仍能收发、
一次内部 HTTP 重试、连续重试、首次失败请求耗时、重叠扣时、作业恢复及工作台读取。
本地模拟接口不调用付费模型。部署后确认 47 个研究可读取、无研究意外重启、原组仍有 5 项。

原生 SQLite 日志会批量落盘，因此没有用它做实时故障信号；这也是改用 stderr 的原因。
[Codex 日志实现](https://github.com/openai/codex/blob/rust-v0.153.0/codex-rs/state/src/log_db.rs)可核对这一行为。

## 比较对象与最终结果

- 单人：`research_token_diagnostic_0920_165129_l2p71_astra_pass1`，纯 pass@k、k=1。
- 四人：`research_0920_exp2_v021_0920_164321_l2p71_astra`，v0.2.1 leader 指导、k=4。
- 模型均 Astra/xhigh，每名 researcher 各 3600 秒有效预算。下面时间使用实验当时记录的口径；
  旧版未完整扣除内部 HTTP 重试，没有事后改写时钟。

| 结果 | 单人诊断 | 四人 v0.2.1 |
|---|---:|---:|
| 搜索最佳耗时 | 0.271 ms | 0.295 ms |
| 搜索 speedup，固定 reference 1.55 ms | 5.7196× | 5.2542× |
| 最终正确性 | 5/5 | 5/5 |
| 最终复测耗时 | 0.339 ms | 0.295 ms |
| 最终 speedup | 4.6903× | 5.2881× |

**搜索阶段单人领先，最终原始成绩四人领先。** 最终 reference 分别是 1.59、1.56 ms，
跨实验主要比较候选耗时，不能直接拿不同 reference 的 speedup 当纯性能差。

单人的最终测量存在明显离群：100 次，min=0.266、mean=0.339、max=7.42、std=0.712 ms。
从公布的均值反推，除最大一次外，其余 99 次的平均约为 `(100×0.339−7.42)/99 = 0.2675 ms`。
因此单个离群值几乎足以解释全部反转。这只是对聚合数据的诊断，**不是修改正式分数**。
源码哈希 `ede752a0ebda5ce98aa50b0fdaa09b2f3ea61176d02a4240510f8ccd4d571cf3`
与 0.271 ms 候选完全一致，没有重现选错候选的问题。搜索时该源码 std=0.0241、max=0.511 ms。

四人最终测量 min=0.288、mean=0.295、max=0.547、std=0.0254 ms。
两次最终作业分别落在 slurmd-62、slurmd-0。没有逐次计时与设备现场证据，不能进一步认定离群是
GPU 干扰、调度、频率变化还是别的原因。评测侧需要单独研究计时稳定性，不应在 RSI 选优层偷偷改统计口径。

此前 v0.1 纯 pass@4 的 L2P71 最终为 0.338 ms。单人搜索的 0.271 ms 相比它对应约 24.7% 的吞吐优势，
相比这轮四人的 0.295 ms 是约 8.9%；最终复测有上述噪声，尚不能把这个搜索优势称为稳定复现的收益。

## 确定存在的差异：每人真正获得的模型工作量不同

| 一小时内 | 单人 | 四人 R1 | 四人 R2 | 四人 R3 | 四人 R4 |
|---|---:|---:|---:|---:|---:|
| 输出 token，含推理 | 61,012 | 40,310 | 45,551 | 42,669 | 39,901 |
| 其中推理 token | 24,593 | 15,592 | 15,638 | 14,939 | 14,526 |
| 完成的模型响应 | 89 | 63 | 56 | 55 | 59 |
| 评测及诊断作业 | 71 | 51 | 44 | 43 | 47 |
| 最外层工具阻塞，分钟 | 21.55 | 16.15 | 15.46 | 15.32 | 14.72 |

四人各自的 token 产出比单人少；单人比四人均值多约 45%。这不代表四人团队总计算量少，
团队仍完成了更多工作，但不是四份与这次单人等量的连续探索。
单人做了更多 GPU 作业，所以累计工具阻塞反而更长；这轮不能用“单人少等 GPU”解释其优势。

原生传输日志的拆分更直接：单人的可匹配 72 次请求，响应头前平均 2.60 秒、中位数 2.36 秒；
四人分别 55–63 次，平均 19.80–21.09 秒，中位数 14.15–15.82 秒。
四人各自累计花在响应头前的时间约 18.3–20.8 分钟。
扣除最外层工具阻塞后，收到响应头后的实际输出速度两边都约 **29 token/s**。
也就是说，主要损失在正常生成开始前，不能解释成多 researcher 下 Astra 本身生成更慢。

这些头前时间包含传输、请求准备、服务端等待和内部重试，不能全部当故障扣除。
四人的日志还各有 13–16 次内部 HTTP 失败，旧计时只对 R2 记了约 94 秒上层故障。
之前同原生客户端、同合成请求的独立转发 6.91 秒 / 工作台转发 43.72 秒对照，
进一步证实其中确有我们自己的传输瓶颈，详见[前次诊断](exp1-and-token-throughput.md)。

## 研究路线具体分叉在哪里

按每人有效时间截断，取团队当时最好结果：

| 有效分钟 | 单人最好，ms | 四人最好，ms |
|---|---:|---:|
| 5 | 0.424 | 0.659 |
| 10 | 0.334 | 0.343 |
| 15 | 0.316 | 0.321 |
| 20 | 0.316 | 0.321 |
| 30 | 0.271 | 0.307 |
| 40 | 0.271 | 0.307 |
| 60 | 0.271 | 0.295 |

两边很早都想到 BF16 高低分解；“多人没有想到核心算法”并不符合记录。
单人在约 6.57 分钟通过静态分块到 0.334 ms，10.25 分钟通过输出布局到 0.316 ms。
它尝试输入预转换后发现更慢，保留直接读取原始 NCHW 的实现。
到 27–28 分钟，进一步把 K=72 的归约拆成 64+16，减少尾块补零和同步，达到 0.271 ms。
最终源码是单卷积 kernel、按行分块、计算时拆分高低位、通道连续的输出布局。

四人 R1 早期通过预拆分输入与 NHWC 重排取得 0.343 ms，后来到 0.321 ms。
预处理实测约 0.039 ms，主卷积约 0.305 ms。R1 也尝试过直接读取 NCHW，
22.27 分钟的具体实现为 0.338 ms，没超过当时的 0.321 ms，于是回到预处理路线。
23.36 分钟缩小 K 到 16 后到 0.307 ms，后续做 Gluon、异步 WGMMA、寄存器、写入策略，
最终取得 0.295 ms。其最终源码仍是预处理 kernel 加卷积 kernel。

这不是“预处理方向错误”的证明：它确实带来过很大的早期收益；也不是说 leader 禁止直接读取输入，
R1 实际试过。问题在于某个直接读取版本没有胜出，之后没有找到单人的那套分块与归约组合。
局部负结果只能否定所测实现，不能排除相邻的数据组织方案。

四人仍保持两类主要路线：R1/R4 做直接卷积，R2/R3 做 Winograd，并比较不同精度表示。
Leader 共 22 次指导、8 次读取原始轨迹；researcher 共 40 次报告。
早期分享 NHWC/权重布局确有收益，后期也发现并修复动态缩放的数值范围问题。
没有看到强迫全员追随同一候选或提前全员收尾的证据。因此这轮不宜再归因于“leader 完全失职”。
较合理的疑点是：直接卷积两条线的早期经验共享，使两人都更多围绕预处理方案优化，
而不是持续保留不同的数据组织和归约方式。轨迹支持这个判断，但无法单独量化它造成多少掉分。

## 这次对照的边界与下一步

单人用独立 HTTP 观察进程；四人用旧工作台共享转发。单人没有 leader 技术指导，四人有。
另外发现诊断代理仅放行 `/responses` 和 `/models`，意外让单人原生 web search 返回 404。
单人后来改读安装版 Triton 文档。已修复 operator 观察器的路由转发，但未热改这次正在运行的实验。
所以这不是一个只改变人数的受控对照；搜索失败也改变了资料来源和时间分配。

目前能确认工程吞吐不足，并能指出产生领先候选的具体实现组合；不能据此宣判协作一定变差，
也不能把全部差距推给运气。下一步应在已修复、同一路由、原生搜索均正常的条件下，先比较纯 pass@1 和
纯 pass@4，再只增加 leader 指导。测量噪声另在评测适配层处理，保持原始结果与规则透明。

原始证据与分析脚本：`.rsi/passk-workbench/operator/single-vs-four-0920/`，含逐人公开轨迹、
完整计时统计、原始请求元数据和两份冻结候选源码；部署记录在 `operator/engineering-fixes-0920/`。
