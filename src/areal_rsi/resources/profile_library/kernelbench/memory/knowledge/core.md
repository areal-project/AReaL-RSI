# 沿数据流寻找收益

先估计输入、输出、参数和中间结果的体量，以及一次完整调用需要读写多少数据。这给出一个粗略的访存成本参照，不能直接证明 kernel 已受显存带宽限制：缓存命中、访问不连续、同步和指令发射也会影响时间。把估计与实测放在一起，找出值得进一步检查的差距。

逻辑维度和物理布局是两回事。连续地址能否被相邻线程高效访问，取决于线程映射和实际 stride，不只是张量名字。改变输出存储布局可能降低写回成本，也可能增加后续消费者的转换成本。视图是否免复制、接口是否允许非连续结果，都应按真实代码和任务要求判断。

复用有不同层次：在寄存器保留局部值、在线程块内共享数据、利用缓存，或跨调用复用合法的准备工作。更大的 tile 可能提高复用，同时增加寄存器和共享内存占用。共享内存也有搬运、同步和访问冲突的代价；较少的全局读写不保证更快。

预打包或布局转换应作为完整计算的一部分测量。参数和输入是否会变化，决定了准备结果能否复用；缓存不能跳过任务要求的计算，也不能在参数变化后继续使用旧值。优先明确语义，再评估节省的重复工作是否值得新增的状态和调用开销。

选择实验时，说明希望减少哪一段数据搬运，并检查是否把成本转移到了别处。若布局已经改善，但整体时间仍没有变化，下一步应重新判断主要瓶颈，而不是不断尝试更多布局。也可以利用同伴的局部计算方法，保留自己的数据组织进行比较。

资料入口：[CUDA 合并访问、有效带宽与共享内存](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html)、[PyTorch Tensor Views](https://docs.pytorch.org/docs/stable/tensor_view.html)。文档中的例子是方法说明，需按当前硬件、布局和执行方式验证。
