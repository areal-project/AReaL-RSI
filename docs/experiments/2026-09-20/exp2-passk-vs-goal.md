# 工程修复后，pass@4 与 goal baseline 仍有什么差异

2026-09-20，0920-exp-2 已结束。比较对象为：

- 当前纯 pass@4：`research_0920_exp2_fixed_0920_181309_v01_l2p71_astra`。
- goal baseline：`codex-full-gpt6astra-rsi8-hour1-20260916T030000/L2P71`。

均为 Astra/xhigh，每人 1 小时有效时间。这里只分析公开进展、代码和工具，以及 usage/时间元数据。
没有向 agent 传入其他 run 的资料，没有修改历史成绩或运行参数。

## 逐人结果：不能只看团队最大值

| 对象 | 探索最好耗时 | 输出 token（含推理） | 推理 token | 完成响应数 | 最外层工具阻塞 |
|---|---:|---:|---:|---:|---:|
| Goal baseline | 0.277 ms | 76,547 | 37,593 | 159 | 10.91 分钟 |
| pass@4 R1 | 0.314 ms | 57,186 | 21,672 | 105 | 22.40 分钟 |
| pass@4 R2 | 0.317 ms | 55,724 | 23,514 | 111 | 22.91 分钟 |
| pass@4 R3 | 0.432 ms | 60,612 | 27,005 | 97 | 20.28 分钟 |
| pass@4 R4 | 0.295 ms | 60,041 | 27,154 | 106 | 21.36 分钟 |

R3 的 0.432 ms 是系统仍未撤回的历史最好。其最后报告明确交付修复非连续输入后的
0.447 ms；检查 0.432 ms 冻结源码仍没有输入连续化，而它并未完整撤回所有受影响版本。
这是 researcher 的候选清理遗漏，不能将 0.432 ms 描述成已覆盖全部额外语义检查的最终交付。

团队最终复测：0.297 ms、5.2525×；baseline 最终：0.280 ms、5.5357×。
两个 reference 分别为 1.56 和 1.55 ms。最终候选耗时差约 6.1%，探索最好差约 6.5%。
但四人中最差者比 baseline 探索最好慢约 56%，不能因为团队最大值接近就忽略它。

每位 researcher 的输出量比 baseline 少约 21%–27%；推理输出少约 28%–42%。
模型不在最外层工具调用内的墙钟时间，baseline 为 51.13 分钟，四人为 37.67–39.94 分钟。
对应输出速度两边均约 25 token/s。这不是纯模型生成速度，但清楚显示主要时间差在工具侧。
所有会话都是一个原生 turn，未发现 compact 事件；本轮差距不能归因于被反复打断或压缩遗忘。

## 找到的新工程瓶颈：工具请求在本地主控排队，越到后期越严重

将原生 journal 的 `tool.started`、RSI 主控的 `tool_started` 事件和本地 job 创建时间对应起来，
可以把“开始调用 run_job 到建立作业”拆成请求抵达主控处理的等待，与 handler 内的输入准备。

| 时间段 | R4 请求开始到主控处理 | R4 handler 内准备 |
|---|---:|---:|
| 前 15 分钟 | 0.72 秒 | 0.04 秒 |
| 15–30 分钟 | 3.24 秒 | 0.08 秒 |
| 30–45 分钟 | 6.49 秒 | 0.12 秒 |
| 最后 15 分钟 | 13.70 秒 | 0.17 秒 |

另外三人的最后一段请求等待分别为 R1 15.48 秒、R2 15.28 秒、R3 11.13 秒。
这段发生在 GPU 作业创建之前，既不是 GPU 排队，也不是模型思考。目前它消耗有效时间。
这也说明仅把 `wait=true` 的结果等待上限从 240 秒改为 10 秒，不能限制整个工具调用耗时。

上一轮独立 HTTPS 转发确实修复了模型网络等待：当前响应头前平均约 2.4–2.8 秒，
旧版约 20 秒，当前也没有发现原生 HTTP 失败。但研究工具桥接仍和研究调度共用工作台事件循环。
同一时间共运行三个研究、12 名 researcher 和三个 leader；另一个研究的同步处理也会拖延这里的请求。

代码与只读 profiling 找到一条明确的重复工作路径：

1. `engine.py` 的事件回调在每次工具完成后同步调用 `_recovery_state`。
2. `PassKActions.state` 重扫历史验证，为每个符合条件的结果重读 `contract_digest` 和撤回集合。
3. 读取 contract 又读取 brief 和整个 run；一次 leader 状态读取再对四名 researcher 重复这些操作。

在协作 L2P71 的结束数据上，一次 leader 恢复状态构建调用了约 22,254 次 `read_text`，
其中 159 次重复获取撤回集合。无 profiler 时约 2.3–2.4 秒；纯 pass@4 的 leader 状态约 1.4 秒。
研究员的一次状态重建也约 0.3–0.5 秒。多个 agent 在同一事件循环上累积这些同步处理，会阻塞工具服务。

只读对照中，仅在同一次状态构建里复用 run、brief、contract 和撤回集合，耗时从
**2.411 秒降为 0.152 秒**，各研究员 best 结果完全一致。该对照只修改分析进程内的方法，
没有改生产代码、运行中的数据或缓存语义。
另测 R4 工作区快照及物化仅约 0.12 秒，排除了“工作区文件太大导致十几秒准备”的解释。

仍需保留归因边界：没有本轮全程主控 CPU profile，不能把每一次 13.7 秒等待精确全归给这个函数。
但请求在主控前延迟、同步重建的重复 I/O 和可复现的消除方式，已足够确认这条工程路径需要修复。

## 工具等待与反馈形态还有差异

GPU 真正运行的平均时间，两边均在数秒量级。本轮 R4 远端作业平均 7.13 秒，本地命令生命周期
平均 11.99 秒，其中远端结束到本地结束平均 3.91 秒。适配 client 每 5 秒轮询，产生可避免的收尾延迟。
这与上述工具请求等待属于不同区间，不应混为 GPU 排队。

baseline 使用短暂 yield 的原生命令，GPU 作业在后台继续；RSI 更常直接 await run_job，
首轮等待会占用模型的工具时间。纯 pass@4 的四人最外层工具阻塞约 20–23 分钟，baseline 约 11 分钟。
后台作业存活时间没有作为模型阻塞计算；这里按原生最外层工具调用到返回的并集计时。

实际进入外层工具返回的序列化文本，baseline 约 12.5 万字符，四人约 42.7–53.0 万字符。
虽然上轮将单段 feedback 正文限制到 3000 字符，元数据、嵌套 JSON 转义和额外读取仍使总返回量偏大。
平均每次输入 baseline 约 6.2 万 token，四人约 10.7–12.4 万；不能把正文截短等同于反馈问题已解决。
这是次要的可测差异，不用它代替已确认的工具等待解释。

## 为什么最差的 R3 会落后这么多

R3 的输出 token 反而是四人最多的，因此不能把它的低分简单归因于思考量最少。

- 约第 6 分钟已有 0.414 ms 的 FP16 方案，随后自行发现大输入溢出并撤回。
- 约第 25 分钟得到 0.424 ms 的 BF16 三乘积，随后发现放大输入/相消问题并撤回。
- 后续主要做范围保护、转换打包、FP32/Winograd 对照和非连续输入检查。
- 第 39–40 分钟的分项诊断显示范围检查约 0.064 ms、卷积约 0.392 ms；优化范围扫描后到 0.432 ms。

baseline 获胜源码仍是**无范围保护的 BF16 三乘积**，另有针对当前形状的实现组合：
权重高低位打包、输入转换的双元素指令、按行分块与行重排、K=72 拆为 64+16、寄存器上限 128。
R4 找到了相近的按行/通道连续输出与 BF16 三乘积，但使用 K32 三块；没有得到 baseline 的整套组合。
R1/R2 后期也在做寄存器、权重预处理和显式 TF32 累加，其结果分别为 0.314/0.317 ms。

baseline 约第 16 分钟已有 0.298 ms，第 40 分钟到 0.277 ms；R4 到约第 29 分钟才达到 0.298 ms。
不能用“修好等待必然找到同一实现”替代实际测试。但较慢的闭环、不同的验证投入，以及未找到的
实现组合均有轨迹证据，不需要先归因于模型在多人身份下变弱。

不能因为 baseline 通过正式测试，就把没有保护认定为覆盖所有数值边界；同样不能宣布已证明
这份 baseline 源码不正确。要比较算法能力，还应采用共同的任务契约和补充测试，保留原始分数。

## 接下来的优先级

v0.2.1.1 的协作改动已独立实现，**没有把这些工程修改混入该版本**。
下一步应先修掉事件循环中的重复状态重建和工具等待，使用稳定、简短的结构化作业反馈，
然后在同一工程版本上比较纯 pass@1 / pass@4。应检查每个 researcher 的工具延迟、模型可用时间、
输出量和进步曲线，而不是只看团队最大值。

单条随机轨迹不保证达到某一次 baseline 的成绩；但当前所有 researcher 都少了约四分之一输出，
并有随历史增长的共同等待，这不是用随机性可以解释掉的公平对照。四人的团队算力更多，
每个人却还没有获得一份等量、同样顺畅的 goal 探索。
