另检查日志中可匹配到的正常 HTTP 请求：反馈可用到收到 HTTP 响应头的中位时间，两次各人仍大致在 3.5–4 秒；收到响应头到首个可观察模型 item，则从旧组约 0.9–1.8 秒增至新组约 3.3–3.9 秒。后者包含服务端等待、首段生成及客户端处理，不能直接叫作纯推理或单纯网络 RTT。

目前能将额外耗时定位到原生响应开始及完成附近，尚不能在已有记录中唯一判定是上游流式服务、网络转发还是 Codex 本身的处理。要进一步区分，需在同一次小型探测中同时记录 SSE 边界和客户端事件，测完直接连接与现有 relay 的差异；现有日志没有完整的原始 SSE 到达时刻。

事件口径参考官方 [Codex App Server 文档](https://learn.chatgpt.com/docs/app-server)：item 完成事件与 thread 用量更新是不同通知。本报告将它们之间的间隔作为端到端观察量，没有将用量通知时间自动当成服务端生成结束时间。

**GPU、回合调度与异常超时分别造成什么影响。**

- GPU 作业耗时和排队不足以解释全部交互下降：晚间 R2–R4 单次作业中位数约 9 秒，与旧组接近。各人累计 GPU 排队约 9–11 秒。
- 晚间 R3 的两次约 5 分钟超时造成额外损失，且存在上一份报告记录的漏扣。R1、R2 没有这类超时，其正常响应仍明显变慢。
- 旧组开始 69 个 agent turn，新组仅 9 个。旧组频繁输出最终答复，再被系统自动续跑；新组更多在一个长 turn 内持续使用工具。系统续跑间隙平均每人约 24 秒 → 2 秒，没有变慢。
- 旧组向 leader 的正式报告为 67 次，新组 23 次。旧组交互中确有更多报告和重复收尾，不能把所有多出来的响应都视为有效探索。
- 新 R2 多用 `kb wait`，旧 R2 多用原生 `write_stdin`，二者都是允许的反馈读取方式。这会影响部分交互构成，但其他三人没有同步切换到 `kb wait`，无法解释全组都有的收尾延迟。

**输出风格没有给出可靠的“模型被换弱”证据。**

只统计公开 assistant 消息，不读取或引用隐藏推理文本：

- 公开消息数：241 → 108。
- 每条公开消息平均长度：125 → 147 字符，没有普遍变短。
- 每次模型响应平均 reasoning token：133.3 → 128.6，变化约 -3.6%。reasoning 占总输出比例从 46.0% 降至 40.9%，但比例还受代码和工具调用输出量影响。
- 两组都使用相近的“观察到什么 → 推测瓶颈 → 下一项实验 → 保留回退版本”的技术叙述。早晨也大量出现“最后一次”“最终确认”之类过早收尾措辞，并非新组独有。
- 内容层面的错误比措辞更值得重视，例如上一报告中 R1 修改未调用函数，却宣称已验证 tf32x3 没有收益。这能证明该次实验推断不成立，但不能单独证明服务端换了模型。

原生 CLI 版本、config.toml、请求中的 codex_config 和日志里的 feature 列表均已核对一致。请求 effort 仍为 xhigh。请求配置和风格相似仍不能证明上游实际路由、模型权重相同。
