# RSI 持续目标执行研发计划

状态：待实施方案。基线：`6e22ab4`（独立 bugfix 已完成并通过端到端验收）。
本文中的新命令、goal 策略和原生登录接入均是计划，不代表当前已经支持。

## 1. 目标体验

用户在项目中输入类似 `/rsi 修复失败测试，保持公开 API 不变`，系统结合当前项目和用户明确提供的上下文建立目标，持续执行、验证和修正。用户可查看进度、追加约束、暂停、恢复或停止；完成时获得可审阅的变更与验证证据。

Codex 和 Web 操作同一个 RSI 后台服务、同一个 run。服务负责执行权和持久化；Codex 提供对话入口，Web 提供进度与产物视图。

默认使用一个执行 Agent；需要独立尝试或并行探索时再增加 Agent。Codex 已承担需求沟通时，直接提交整理后的目标，避免重复启动 Interaction 对话。保留独立 CLI/Web 的需求沟通入口。

## 2. 已有基础与已完成修复

可以复用：ResearchSystem、任务/候选/验证记录、工作区隔离、原生 Runtime、持久事件、后台工作台、HTTP 控制、暂停/恢复、作业执行、候选导出。

已修复：最终验证取消竞态、控制操作跨进程互斥、未完成创建的安全重试、Runtime 环境与工具展示参数传递、初始化资源清理、嵌套配置校验。

基线验证：276 个 Python 测试、63 个子测试、14 个前端测试通过；17 项因环境跳过，Ruff/Mypy 通过。真实模型经原生 Codex 修改算术程序，搜索和自动最终验证均为 1.0，无需故障恢复；HTTP 故障注入、重启读取、导出和停止/删除通过。

## 3. 架构约束

- 延用 api/ 契约、infra/ 实现、ui/ 入口的分工，不增加顶层 goal/app/base 层。
- 延用 ResearchSystem 和现有 Run 身份；目标附着于现有 run，不另建平行的 GoalManager、GoalRun 或执行服务。
- 扩展 TaskBrief/研究记录，固定结构使用具名数据类型；JSON 留在传输和插件边界。
- goal 与 passk 具有不同的执行策略。passk 保持固定实验条件；goal 接受显式修订。首次不改变已有实验的默认行为。
- 策略放 coordination/policies，调度和生命周期留在现有 coordinator/engine；项目操作优先复用工作区和存储能力。
- UI 和 Codex 接入只调用公共控制接口，不直接修改状态文件，也不各自持有一个执行循环。
- 历史记录、候选摘要、冻结协议和 source-lock 不随新功能重写。

## 4. 待研发功能

| 编号 | 功能 | 实现范围 | 验收标准 |
| --- | --- | --- | --- |
| F01 | 一句话启动 | 目标文本、当前目录、可选预算；推导需求与合理默认值，关键缺失信息才提问 | 无需先编写 ResearchConfig 即可启动真实任务 |
| F02 | 项目与会话上下文 | 当前仓库、分支、未提交修改、项目约束、用户指定的文件和对话摘要；建立 Codex 会话与 run 的关联 | 能解释任务采用的上下文；重复发送不创建重复 run |
| F03 | 目标与验收契约 | 描述目标、约束、验收条件、预算和目标版本；支持命令、清单、交付物及人工确认 | 未满足必需验收项时不能声明成功；证据可追溯到目标版本和产物 |
| F04 | goal 执行策略 | 执行、验证、修正、继续；合理结束一次回合不等于结束目标；按需使用多 Agent | Agent 一次回复结束后仍推进未完成目标，不依赖用户反复说“继续” |
| F05 | 状态与预算 | 统一运行/暂停/等待/阻塞/完成/取消的领域语义及对外映射；预算耗尽独立呈现 | 暂停不算完成；恢复不清零已消耗预算；延长预算必须显式记录 |
| F06 | 阻塞与故障分类 | 临时故障退避重试；持续无进展或缺少外部条件时记录阻塞；明确等待事件和恢复条件 | 不无限空转、不重复提交同一副作用；用户能理解为何等待及如何恢复 |
| F07 | 中途指导与目标修订 | 追加约束、修改方向、补充信息；持久化新版本，处理在途作业及已有验收结果 | 新指令在明确的安全边界生效；过期结果不能用于完成新目标 |
| F08 | 持续任务恢复 | 重启后的执行恢复、工具/作业去重、会话恢复和状态重建；继续沿用执行锁 | 强制终止并重启后继续同一目标；不自动恢复用户主动停止的任务 |
| F09 | 项目工作区 | 绑定任务基线，处理已有修改，支持独立 worktree；约定并行 Agent 的写入范围 | 不覆盖原有修改；并行工作产生的冲突可发现、可处理 |
| F10 | 成果交付 | 可审阅 diff、修改说明、验收证据、产物；应用回原项目并检查基线变化 | 应用前后均可验证；冲突不能静默覆盖；提交/发布按用户授权处理 |
| F11 | 公共控制 API | 复用已有创建/查询/暂停/恢复/停止；补充目标修订、阻塞回复和成果操作；共用请求校验 | CLI、Codex、Web 的权限、状态检查和幂等语义一致 |
| F12 | 后台服务接入 | 启动或复用服务，检查版本与数据目录，返回 run_id 和 Web URL；按事件游标查询 | 关闭发起终端后任务仍由服务执行；两个客户端看到同一个 run |
| F13 | Codex 薄入口 | 目标发起、状态查询、指导、暂停、恢复和停止；携带工作目录、绑定当前会话 | 在 Codex 内完成主要交互，不需要复制 run_id 或手写 HTTP 请求 |
| F14 | Web goal 视图 | 展示目标版本、验收清单、当前动作、预算、阻塞、证据和 diff；复用现有时间线 | Web 操作能反映到 Codex 查询；运行和历史记录显示一致 |
| F15 | 进度通知 | 基于已有持久事件补充客户端通知；完成、阻塞、需决策时通知，其他时间提供简洁进度 | 断线重连可补读；不重复通知、不频繁刷屏 |
| F16 | 复用 API Key 配置 | 现有 api_key_env 已可复用变量；补充显式凭证来源选择、匹配的服务地址与模型、启动诊断 | 无需复制为另一份 RSI_API_KEY；不把凭证写入目标、事件或前端数据 |
| F17 | Codex 原生登录 | 为 Codex 后端接入原生账号认证；委托原生机制处理登录刷新，处理失效与不可用情况 | 该模式无需 RSI API Key；重启与凭证刷新验证通过；不静默切换身份或计费方式 |
| F18 | 安装与运行说明 | 安装/升级、服务发现、数据目录、配置优先级、故障诊断和恢复说明 | 按文档从干净配置完成一次目标任务，已有 passk 入口仍正常 |

F16 与 F17 分开实现。复用某个服务的 API Key 需要使用匹配的服务地址和模型；原生 Codex 登录不是普通 API Key。目标模型若使用另一服务，仍保留独立配置。

## 5. 控制交互草案

以下是用户交互语义，命令拼写在入口验证后固定；内部统一调用 F11，不另建一套控制协议。

| 操作 | 语义 |
| --- | --- |
| `/rsi <目标>` | 为当前项目创建并启动目标；必要时先补齐关键条件 |
| `/rsi status` | 查看绑定目标、进度、预算、验收结果和 Web 链接 |
| `/rsi guide <补充>` | 补充事实或追加指令，必要时形成目标修订 |
| `/rsi pause` | 暂停推进，明确在途作业如何处理，保留恢复位置 |
| `/rsi resume` | 继续暂停或已解除阻塞的目标，保留历史预算和证据 |
| `/rsi stop` | 明确终止当前执行；不会被后台自动恢复 |
| `/rsi result` | 查看成果、diff 和验证证据，执行显式授权的应用操作 |

Codex 是否允许以原生斜杠命令注册 `/rsi`，需要先验证目标客户端版本的扩展能力。核心先提供 CLI/服务 API；Skill 或插件作为薄接入。命令展示方式不影响后端设计。

目标修订必须明确：哪些在途作业可继续、哪些需要取消，以及哪些旧验收结果仍可使用。普通聊天、修改目标、修改实验配置不能混成同一个无结构操作。

## 6. 实施阶段与依赖

| 阶段 | 内容 | 交付门槛 |
| --- | --- | --- |
| M0 接口与可行性确认 | 定义目标状态、预算、修订和验收语义；验证当前 Codex 扩展入口与冻结 Runtime 的原生认证能力 | 确定可落地入口；记录原生认证的支持条件和明确限制 |
| M1 自然语言与项目接入 | F01/F02/F03、F09 的任务基线与单工作区、F11 的创建与查询 | 一句话建立有明确范围和验收条件的任务，可通过现有服务运行 |
| M2 持续执行闭环 | F04/F05/F06/F08、F11 生命周期操作 | 自动继续、预算停止、阻塞恢复、崩溃恢复及验收停止通过 |
| M3 指导与成果交付 | F07、F09 并行冲突处理、F10、F11 修订与成果操作 | 中途改方向不会错误复用旧结果；成果可审阅并应用回项目 |
| M4 Codex/Web 一致体验 | F12/F13/F14/F15 | Codex 发起和指导，Web 实时观察或控制；服务重启后会话关联仍存在 |
| M5 凭证接入与交付 | F16/F17/F18、兼容性验收 | API Key 与原生登录分别验收，安装和历史 passk 使用路径可复现 |

F16 可与 M1–M4 并行；F17 在 M0 完成可行性确认后独立推进。原生斜杠扩展或原生认证若受上游限制，须明确标为未交付，不能以普通 API Key 路径冒充验收通过。

最小可用版本覆盖 M1/M2 和单工作区的可审阅成果：一句话启动、持续执行、明确停止或阻塞、重启恢复，以及已有 Web 中的进度查看。多 Agent、复杂成果合并和完整 Codex 入口随后交付。

## 7. 端到端验收

复用现有集成测试，新增用例围绕行为和故障，不穷举字段或转发方法。

1. **正常完成**：在含确定失败测试的仓库发起目标，真实模型修复并通过验收，输出 diff 与命令证据。
2. **保留原有修改**：起点有用户未提交修改，任务执行和成果应用后仍保留这些修改。
3. **中途修订**：执行中追加“不能修改公开 API”，新版本生效，旧版本证据不会使新目标错误完成。
4. **暂停与预算**：暂停/恢复不丢进度、不重置预算；预算耗尽明确停止推进，显式扩充后才继续。
5. **真实阻塞**：缺少必要输入或依赖，停止无效重试并说明恢复条件；补充后继续原目标。
6. **崩溃恢复**：在作业提交和工具返回等边界终止服务，重启后不重复执行已提交的副作用。
7. **双端一致**：Codex 发起，Web 观察和暂停，再从 Codex 恢复；同一 run 的状态及事件一致。
8. **完成边界**：完成后不会再次自动运行；用户 stop 不会被自动恢复；旧工具回调不影响最终验收。
9. **成果冲突**：目标执行期间原仓库发生变化，应用成果时检测冲突并保留双方修改。
10. **凭证路径**：共用 API Key 和 Codex 原生登录分别验证；凭证失效时准确报错，记录和 UI 不暴露凭证。
11. **实验兼容**：现有 passk 仍保持冻结配置、独立尝试、候选验证及历史记录兼容。

跨模块交付运行 make check；主要里程碑运行真实模型 + 真实本机作业 smoke，保存 run、事件、diff、验收输出及报告，明确模拟部分和跳过环境。
