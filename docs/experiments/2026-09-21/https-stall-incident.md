# 0921-exp-1：一次近 40 分钟的模型请求停滞

本次已经验证了一个工程问题：模型请求长时间没有数据时，HTTPS 转发没有空闲超时，原生客户端也没有及时发出失败事件。研究员保持 running，既不探索，也没有触发 API 等待扣除。仅替换转发进程后，同一个 Codex 进程恢复了输出。

## 现场与恢复

- 对照组：`research_batch_35c0064966644a0f_1_l2p71`，v0.2.1.2 / Luna xhigh。
- 研究员：`research_9acad3b6bc302da6b1b28c5e`，数据布局与访存研究员。
- 19:48:07：最后一条 usage，随后发出的请求一直未返回。
- 19:48:15：此前的 `kb eval model_new.py` 已完成，正确性通过，5.20 ms。此后没有待完成工具或 GPU 作业。
- 20:17—20:27：连续采样没有模型输出、工具调用或网络流量。Codex 和 relay CPU 接近 0；relay 主线程在等待 kqueue，未发现同步计算占满事件循环。
- 20:28:00：仅终止旧 relay PID 93292，用新 relay 在原端口 65061 接管。Runtime worker PID 93418、Codex PID 93461、原生 session、工作文件和 prompt 都保留。
- 20:28:00：原生客户端立即产生 apiRetry 事件，start 回溯至 19:48:07。
- 20:28:02：请求恢复，apiRetry 区间关闭。
- 20:28:04 起：重新产生原生输出；20:28:22 提交进展报告，此后继续读取代码、研究。
- 有效时间账本自动排除 2395.026 秒 API 等待（39.92 分钟）；没有手工修改预算。

证据保存在本地 batch 的 `progress-probe/`：`diagnosis.json`、进程采样、`observations.jsonl`、`recovery.json` 和 `recovery.log`。恢复使用的临时 relay 在原 worker 退出后自动结束。

## 能确定与不能确定的部分

替换转发后原会话立即重试并恢复，证明这段空白来自请求链路停滞，不能解释成正常深度思考、GPU 排队或研究员主动停下。

原实现只有 CONNECT 建连的 10 秒超时，后续双向复制和连接关闭没有等待上限。Runtime 的 86400 秒是整回合预算，不是单次请求的空闲超时，无法防止这种故障吞掉研究预算。已有 API 计时逻辑需要收到重试事件才会生效；这次直到人工断开连接才收到该事件。

最初请求为什么卡住，尚不能区分远端服务、中间网络或本地系统网络层。`lsof` 曾显示上游 CLOSED、下游 ESTABLISHED，但仅凭 socket 状态不足以把责任归到某一层。当前证据也不支持“并发必然造成此次故障”。

上一批三题并发的 v0.2.1.4 L1P77 中，同身份研究员在 19:08:58 后直到 19:23:12 被系统停止也没有新事件。这是类似的约 14 分钟尾部空白，但没有对当时连接做恢复实验，不能视为同一根因已被证明。

## 修复范围

- HTTPS 转发新增 300 秒双向无数据超时。按实际传输刷新，不限制活跃流的总时长。
- 任一方向结束后取消另一方向，连接关闭最多等待 2 秒，之后释放 socket。
- 增加连接元数据日志：开始/结束时间、目标 host:port、上下行字节数和退出原因。不解密 TLS，不记录请求、响应正文或凭据。
- 进展探针继续每 30 秒检查；没有待完成工具/作业且静默超过 3 分钟时提示，超过 10 分钟标记疑似停滞。
- 六项定向测试通过，覆盖隔离、字节转发、父事件循环阻塞、上游 EOF、无数据超时及持续流量刷新超时。

修复已用于本次故障研究员的替代 relay。其他运行中的 relay 未重启；后续创建的 relay 会加载新的网络模块。持久日志的 Runtime 配置将在工作台下次重启后完整生效。

## 对实验解读的影响

本轮不能当作完全干净的 skill 对照：虽然恢复后故障时间自动扣除了，但这名研究员错过了团队前约 40 分钟的协作窗口。早期能力和信息共享顺序已经改变。此次故障可以解释这条研究线几乎空白，不能据此把其他研究员的全部分差也归因于网络。
