# v0.2.1.2 Astra 七题复盘

七题均已完成，每题四名研究员各一小时有效时间。结论：按本轮约定的标准，可以进入 Luna 七题泛化测试；暂不追加 Astra 复测，也不触发 v0.2.1.1 的条件补测。v0.1 Astra 继续暂缓。

## 结果

单位为 ms，越低越好。主要对比双方一小时内的探索最好耗时，最终确认单列，不使用漂移的 reference 直接比较跨 run 的 speedup。

| 题目 | 新版探索 | 新版最终确认 | Goal 首小时探索 | Goal / 新版探索 |
| --- | ---: | ---: | ---: | ---: |
| L3P10 | 6.37 | 6.39 | 10.9 | 1.711 |
| L2P71 | 0.307 | 0.308 | 0.277，已知反例失败 | 0.902 |
| L1P63 | 4.83 | 4.83 | 5.89 | 1.219 |
| L1P77 | 0.483 | 0.483 | 0.397，已知反例失败 | 0.822 |
| L2P14 | 2.52 | 2.51 | 2.85 | 1.131 |
| L3P19 | 0.488 | 0.484 | 0.501 | 1.027 |
| L3P28 | 0.0541 | 0.0547 | 0.0882 | 1.630 |

七题正式记录的性能比几何平均为 **1.166**，五题更快、两题更慢。L2P71、L1P77 的旧 goal 冻结源码在相同补充反例上失败，新产物通过；两题仍列出正式分数，但不计入无已知反例的对照汇总。其余五题几何平均为 **1.316**，五题均领先。通过有限诊断不等于证明所有合法输入都正确。

L3P10 对一小时边界敏感：goal 的 10.9 ms 在约 59.66 分钟完成，9.28 ms 在 60.50 分钟，7.0 ms 在 64.02 分钟。不能拿它两小时的最终结果当一小时 baseline。即使去掉 L3P10，剩余六题正式比值几何平均仍为 1.094；其中四个可比题为 1.233。优势不只来自这一题，但这轮仍没有足够重复试验证明统计显著性。

L3P19 的探索优势只有约 2.7%，不能因为其最终确认 0.484 ms 对 goal 最终 0.618 ms 就夸大收益。旧 goal 当时按波动的 reference 选中了较慢源码，首小时实际曾达到 0.501 ms。L3P28 的旧 goal 也存在类似选优偏差，这里使用较好的 0.0882 ms 对照。

L1P63 相比 v0.2.1.1 的最终 4.66 ms 没有进步，本轮为 4.83 ms。旧 v0.2.1.1 L2P71 有撤回遗漏，不能直接以其界面成绩作为无争议对照。按用户约定，新版不必每题或每次都胜过 v0.2.1.1。

## 从轨迹看到的收益

- **L3P10 不再只有第一位解出正确性的人继续突破。** 算法研究员提出统计量的实现方向，布局研究员做独立诊断并提供原始依据，几条路线在约 36–39 分钟通过。综合研究员最后才通过，但继续自己的布局优化到 6.37 ms，成为最终最好。共享之后仍有独立增量。
- **L3P28 的经验往返有实际效果。** 执行研究员先发展 PDL；布局研究员将它用于自己的实现，再改进 LN 关键路径，75.0→57.6 μs。leader 核读源码后把局部方法传回执行研究员。综合研究员的 Welford 实现也保留，后来采用 leader 从源码中发现的参数预取机会，61.2→57.6 μs，最终 57.5 μs。
- **问题和修法的传播范围确实分开。** L3P28 的首阶段 PDL 同步问题最初只增加执行研究员核查；来源研究员复现反例、验证普通首阶段的修法后，leader 才以同一经验 ID 的 positive 记录分享给相关研究员。错误候选按明确 ID 批量撤回，修复版本继续参赛。
- **落后路线没有一律被替换。** L3P28 算法研究员一直保留 cooperative 单 kernel，通过双缓冲、整块搬运和参数预取到 75.0 μs。最终四人的保留最好为 57.5 / 75.0 / 54.4 / 54.1 μs；均低于旧 goal 的 88.2 μs，但四种实现的差距仍然明显。

身份提供了不同的观察顺序，没有强制四个人永远使用不同算法。算法研究员也可以放弃不划算的变换，转向其他完整实现；这符合本轮设计。

## 仍然存在的问题

L2P14 最后明显收束到相近的精确 TMA 计算与融合归约，布局研究员也承认最后最好主要复用同 run 的结构。早期身份差异没有自动转化为四条长期独立的路线。不过团队的探索结果仍比 goal 快约 13.1%，不能仅凭趋同断言共享有害。

L2P71、L1P77 都花了很多时间检查数值域、修复范围保护、撤回旧候选；L3P28 后半程也有同步与 graph 生命周期检查。这些工作解决了真实反例，同时确实占用优化时间。共享修复仍可能让多人短时间做相近的迁移和验证，不能把这种成本当作零。

L3P28 最后约一两分钟，有人停止提交可能来不及结束的 GPU 配置，整理产物和记录。此前四条线持续推进，leader 没有早早要求只做复测。尚有可恢复的工具使用错误，例如把撤回 batch ID 当成可引用记录；没有形成持续阻塞。

## 工程与对照边界

初次 r1 因经验引用类型错误中止；r2 的 L2P71 出现明确反例，但临近停止时缺少 leader 直接撤回权限，最终误选了该系列。两项记录都保留。修复后只重跑 L2P71，主结果使用 r3，不在多次运行中按分数挑最好。其他题沿用已完成的原试验。

后期共同工程更新减少了 package runtime 不使用的 recovery snapshot 重建。三题并发扩展的最后十五分钟，报告中位等待约 1.06–1.24 秒；L3P28 单题时为 0.216 秒。各人输出大多约 8–9 万 token，旧有明显少输出的问题没有重现。扩展研究使用同一 r4 版本，运行期间未改实现或 Prompt。

七题获选源码均与候选快照、选优记录、最终回执匹配，且未撤回；获选验证均发生在个人预算结束前。各波结束后已确认远端作业终止。驱动报告名称、计算能力、显存和 PyTorch/Triton 版本与 goal 对照一致；这不保证瞬时负载和时钟完全相同。

因此，这一轮支持的是**当前工程与 v0.2.1.2 组合相对 goal 的综合收益**。没有同工程的新 Astra v0.1 七题控制组，不能把全部收益单独归因于身份。按用户要求，不为补这个控制组恢复已暂缓的实验。
