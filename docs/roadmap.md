# 研发计划

状态：2026-09-28 草案。顺序按依赖和验收门槛安排；人日仅估算工程实现，不包含排队、模型下载与正式训练时长。

| 阶段 | 预计工程量 | 交付 | 退出门槛 |
| --- | ---: | --- | --- |
| P0 契约与冻结 | 2–3 人日 | 最小 `api/` 契约、ToRL 转换/五组划分、不可变 manifest、实验规格 | 重复/泄漏/篡改测试通过；模型/任务/工具/验证器身份可审计 |
| P1 同一 TIR 执行路径 | 3–5 人日 | `H0` 快照、AReaL train/eval 共用 prompt、受限计算器、Slurm worker 预检 | 目标 worker 完成真实 `M0H0` 基线和 A/A 复测；训练/评测摘要相同 |
| P2 Harness 搜索 | 3–5 人日 | 单研究员隔离工作区、候选快照、开发反馈、独立选版 | 至少一个有效 `H1` 候选及逐题轨迹、成本和确定性选择回执 |
| P3 GRPO 训练 | 5–8 人日 | 固定 `H1` 的 AReaL recipe、作业幂等/恢复、rollout 和检查点收据 | 奖励方差有效；真实 Slurm 至少一个 step；`M1` 可重载且来源可追溯 |
| P4 评测与递归 | 3–5 人日 | 2×2 配对评测、封存门槛、原子晋升/拒绝、回滚、下一代起点 | 真实逐题报告；未泄漏 sealed；成功或无增益均能重放决定 |
| P5 SFT 对照 | 5–8 人日，独立排期 | 审查轨迹、loss mask、AReaL SFT、等预算比较 | 真实 SFT 检查点和 rollout，按 P4 同一门槛评测 |

P0–P4 粗估 16–26 人日。数据合成在首个闭环之后：新题先去重、验证答案、审查难度/分布，再冻结成下一版 TaskSet；它不能静默扩充当前实验的题集。

## 实施顺序

1. **确认部署事实**：拿到 Slurm 分区/节点布局、共享文件系统、模型及镜像/环境；在集群运行 `sbatch` 探针和一条真实 TIR rollout。若资源尚未就绪，先完成 P0 与 CPU 故障测试，P1–P4 保持未验收。
2. **冻结实验**：记录源数据许可证和官方划分，预登记题集、种子、候选/训练/评测预算、主目标与晋升阈值。开始搜索后不改同一实验身份。
3. **按垂直切片实现**：先 `M0H0` 完整一题的题面→执行→验证→记录，再扩展成五组题和候选搜索；最后接训练与发布。每片都留真实轨迹和故障用例。
4. **先小后大**：控制器校验、Slurm worker 烟测、单 step 训练、预算内训练、四组评测、sealed 一次决定；每级失败保留原始日志与状态。
5. **形成第二代**：读取第一代发布指针启动新 generation，证明父模型/Harness、题集、预算与决策谱系一致。

## 分工与依赖

RSI 仓库拥有题集、Harness、实验控制、评测和发布；AReaL 仓库只承载通用 TIR/训练能力和必要的上游修复。首版沿用 AReaL 已有 SlurmScheduler，不维护 Ray 代码。候选研究员只接触允许的反馈。封存评测和发布由控制器执行，研究员无对应写权限。

当前两项关键外部依赖是目标 Slurm 环境与模型资产。没有它们仍可做 P0、部分 P1、CPU 控制测试；不能据此宣称 GPU 端到端跑通。
